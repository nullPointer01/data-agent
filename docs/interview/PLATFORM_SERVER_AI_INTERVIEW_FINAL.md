## 2. 三个必须讲熟的项目故事

每个故事按照 `Situation -> Task -> Action -> Result -> Reflection` 组织。

### 2.1 服务端故事：千万级数据任务

重点不是“用了多线程”，而是讲清楚以下问题：

```text
任务如何分片
如何控制并发和下游压力
如何保证幂等
失败如何重试和补偿
服务重启后如何恢复
如何通过指标确认没有积压或漏数
```

回答模板：

> 面对大数据量拉取任务，我不会直接开大量线程。首先按照稳定业务键或时间范围拆分任务，并把任务状态持久化；执行端使用有界线程池和限流控制下游压力；写入使用业务唯一键保证幂等；可重试异常采用有限重试，超过阈值进入失败任务表或人工补偿；最后通过成功数、失败数、积压量、耗时分位数和数据对账确认完整性。

注意：具体分片键、线程数和指标必须按照你的真实经历回答，不要临场编数字。

### 2.2 稳定性故事：Full GC / OOM 排查

标准路径：

```text
告警和现象
 -> 判断 CPU、内存、线程还是外部依赖
 -> GC 日志 / jstat / heap dump / 线程栈
 -> 找到大对象、缓存、队列或线程池问题
 -> 修改代码或容量参数
 -> 压测与线上指标验证
```

回答模板：

> JVM 问题我会先区分是内存泄漏、瞬时大对象还是配置不匹配。通过 GC 日志观察晋升和停顿，通过 Heap Dump 比较对象数量和引用链，再结合业务流量、线程池队列和缓存变化定位根因。修复后不能只看服务启动成功，还要对比 Full GC 次数、Old 区占用、P95 延迟和错误率，确认问题真正消失。

### 2.3 AI 故事：模型“只说不调用”

> 不同模型执行同一个 ReAct 问题时，有的模型会输出“我先查询一下”，但没有产生原生 Tool Call，系统会误判成最终答案。我把工具决策轮改为读取完整的结构化模型响应，确保能够拿到 `tool_calls`；同时增加 intent-without-action 守卫，发现模型表达调用意图但没有执行时，注入一次明确纠偏，最多两次，避免无限重试。这个问题让我认识到，Agent 的难点不是写一个 while 循环，而是处理不同模型的协议遵循差异、循环收敛和失败预算。

边界：这是个人项目中的工程验证，不要说成大规模线上指标提升。

### 2.4 AI 可观测性故事：流式路径缺少 Trace

> 我发现同步 Orchestrator 有执行轨迹，但默认流式 ReAct 的 `done` 事件没有 `traceId`，用户反馈无法关联到具体执行过程。我沿着流式入口、ReAct 循环和 SSE 事件定位，补充了迭代轮数、工具调用数、成功状态和 Trace 落库，并把 traceId 放入 done 事件。改造后能够从用户反馈追溯到模型调用、工具执行和失败位置。这个改造体现的是从“有最终答案”向“过程可复现、可审计”演进。

## 3. Data Agent 项目主线

### 3.1 一分钟介绍

> Data Agent 是一个面向企业数据分析场景的 AI Agent 平台。用户可以上传文件、维护知识库、配置数据源和模型，再通过自然语言进行知识检索、SQL 查询、计算和图表生成。
>
> 请求进入 Runtime 后，会根据命令、指定 Agent、指定 Skill 等条件路由；核心执行有 ReAct 和 Orchestrator 两种模式。ReAct 让模型动态选择工具并根据 Observation 继续推理，Orchestrator 负责意图识别、任务拆分和专家路由。
>
> RAG 使用 Milvus 向量召回和全文召回，再进行 RRF 融合、规则重排、父上下文补全、压缩和引用。工程治理包括模型重试熔断、Token 配额、SQL 只读、租户隔离、RBAC、SSE 和执行轨迹。

### 3.2 一次请求的主链路

```text
HTTP/SSE 请求
  -> AgentRuntimeService 路由
  -> Orchestrator 或 ReAct
  -> RAG + Memory + 文件上下文
  -> 模型接收消息历史和 Tool Schema
  -> 模型返回 Tool Call
  -> AgentToolInvoker 执行受控工具
  -> Observation 回填消息历史
  -> 模型继续决策或生成最终答案
  -> SSE / Response 返回
  -> Token / Trace / Audit 落库
```

一句话定义 Agent：

> Agent 不是更会聊天的模型，而是由模型驱动的受控执行系统。模型负责理解和选择下一步，工具连接真实世界，RAG/Memory 补充上下文，Runtime 负责循环、权限、预算、错误恢复和可观测性。

### 3.3 ReAct 和 Orchestrator

```text
Orchestrator：控制层，决定谁做、拆几步、依赖关系是什么。
ReAct：执行层，面对开放问题，动态决定调用哪个工具、调用几轮。
```

为什么同时存在：

> 全部使用 ReAct 会导致路径、成本和交付物不稳定；全部使用 Orchestrator 又需要提前知道流程，无法处理探索性任务。所以已知、稳定、可拆分的流程交给 Orchestrator，未知或路径依赖中间结果的问题交给 ReAct，没有合适专家时也由 ReAct 兜底。本质是“外层确定性编排，内层概率性执行”。

当前真实情况：

- 普通同步请求优先走 Orchestrator。
- 默认流式请求目前直接走 ReAct，两条路由尚未完全统一。
- Orchestrator 默认以规则做意图识别和规划，LLM 意图识别、LLM 规划默认关闭。
- 编排计划支持阶段和并行描述，但主多任务循环当前仍然顺序执行，不能宣称已经完成真正的多专家并行。

### 3.4 ReAct 轮数

当前一轮表示一次主要模型决策：

```text
调用模型
 -> 有 Tool Call：执行所有工具请求并回填结果，继续下一轮
 -> 无 Tool Call：把模型文本作为最终答案，停止
```

`MAX_ITERATIONS = 8` 是经验性安全上限，不是理论最优值。生产设计不能只限制轮数，还要联合限制：

- 最大模型调用次数。
- 最大工具调用次数。
- 最大 Token 和费用。
- 最大执行时间及单工具超时。
- 相同工具和参数的重复次数。
- 每类错误的恢复预算。

科学确定方式：建立代表性任务集，记录成功任务的轮数、工具数、Token、耗时和停止原因，以 P95 设置软限制，再增加少量恢复余量作为硬限制。

### 3.5 RAG 主链路

```text
入库：文件解析 -> 结构/语义/父子分块 -> Embedding -> Milvus + 全文索引

查询：规则 Query Rewrite
   -> 向量召回 + 全文召回
   -> RRF 融合
   -> 轻量规则重排
   -> 父上下文补全
   -> 按字符预算压缩
   -> 引用注入 Prompt
```

为什么混合检索：

> 向量检索擅长语义相似，但对订单号、字段名和专有名词容易漂移；BM25 擅长精确词项，但处理同义表达较弱。两路召回互补，RRF 使用排名而不是直接混合不同量纲的原始分数。

RRF 公式：

```text
score(d) = Σ 1 / (k + rank_i(d))
```

当前 `candidateTopK=20`、最终 `topK=6` 是候选召回和上下文预算之间的经验基线，需要通过离线评估校准，不能说是理论计算结果。

### 3.6 文档解析和分块

当前已经完成：

- 按 PDF、DOCX、Excel、PPTX、文本、图片选择解析器。
- Markdown 标题、段落、表格、代码、列表结构识别。
- 按句子边界合并，超长块才强制切分并 overlap。
- 子块携带章节、字符范围、结构标记和父级范围。
- 小块用于召回，命中后补父级上下文。

生产设计的核心观点：

> 原始文件和结构化 Document AST 才是事实源，向量块只是索引。文本按章节切，表格按“重复表头 + 行组”切，图片通过 OCR、坐标和视觉描述补充语义；召回后根据文档、页码、区域或行列回源。精确表格计算应交给 SQL/Python 工具，RAG 只负责定位数据。

当前边界：

- PDF 当前主要用 PDFBox 抽纯文本，版面、表格和图片结构没有完整恢复。
- Word 段落和表格的原始穿插顺序可能丢失。
- Excel 尚未完整保留合并关系、字段类型和行列元数据。
- 图片解析当前是占位符，没有真正 OCR/VLM。

### 3.7 Memory

```text
Working Memory：当前任务中间状态。
Short-term Memory：近期会话和事实。
Long-term Memory：长期可检索的稳定记忆。
User Profile：偏好和画像。
```

RAG 面向企业知识和文件，Memory 面向用户、会话、偏好和历史结论。两者可能都进入 Prompt，但来源、生命周期、权限和衰减策略不同。

### 3.8 当前项目可讲与不可吹

| 主题 | 可以讲 | 不要讲成 |
|---|---|---|
| 多模型 | 配置默认模型、显式 modelId、OpenAI 兼容接入 | 按成本质量自动路由、自动切备用模型 |
| Rerank | RRF 后做关键词、来源等规则加权 | Cross-Encoder 或 LLM Reranker |
| Query Rewrite | 规则清理、关键词与查询变体 | LLM 多查询扩展 |
| Context Compression | 按章节、句子、字符预算裁剪 | LLM 摘要压缩 |
| 工具数量 | 当前十余个受控工具 | 固定宣称某个历史版本数字 |
| 生产化 | 有权限、审计、配额、重试、熔断、指标和测试 | 已经过真实大规模生产流量验证 |

## 4. AI 与 Agent 高频八股

### 4.1 Transformer / Attention 是什么

> Transformer 用注意力机制建模 Token 之间的关系。Self-Attention 中，输入映射为 Query、Key、Value，使用 Query 和 Key 的相似度计算权重，再对 Value 加权汇总。多头注意力让模型从不同子空间学习语义、位置和依赖关系。

加分点：推理时历史 KV 可以放入 KV Cache，减少重复计算，但上下文越长，显存和推理成本仍会增加。

### 4.2 Token、上下文窗口、Temperature、Top-p

- Token 是模型处理文本的基本单位，不等同于字符或单词。
- 上下文窗口包含输入、历史、RAG、工具结果和输出预算。
- Temperature 越低输出越稳定，企业任务一般偏低；越高越有随机性。
- Top-p 是核采样，只在累计概率达到阈值的候选中采样。
- 生产环境不能靠无限加上下文解决问题，会增加成本、延迟和注意力稀释。

### 4.3 预训练、SFT、RLHF/DPO、RAG 怎么选

- 预训练学习通用语言和知识。
- SFT 用指令数据训练模型遵循任务格式和行为。
- RLHF/DPO 用偏好数据对齐回答风格和安全性。
- RAG 在推理时注入外部知识，适合知识频繁更新、需要引用和权限隔离的场景。
- 微调适合稳定行为、风格、格式或领域任务，不适合频繁更新事实。

回答“RAG 还是微调”：

> 知识更新和事实引用优先 RAG；稳定行为和输出风格可考虑微调；两者不是互斥关系。

### 4.4 什么是 Embedding

> Embedding 把文本映射成稠密向量，使语义相近的文本在向量空间距离更近。常见相似度包括余弦相似度、点积和欧氏距离。入库和查询必须使用兼容的模型、维度和归一化策略，否则结果不可比较。

维度不是越大越好，要综合模型质量、存储、检索延迟和索引参数评估。

### 4.5 BM25 和向量检索区别

> BM25 基于词频、逆文档频率和文档长度做稀疏检索，适合精确词项；向量检索基于语义表示，适合同义表达和语义相关。两者不是一回事，也不是互相替代关系。

### 4.6 Function Calling 怎么工作

> 后端把工具的名称、描述和参数 JSON Schema 交给模型；模型返回结构化 Tool Call，后端校验权限和参数后执行，再把 Tool Result 作为消息回填。模型只提出调用请求，不应该直接拥有数据库或网络权限。

工具设计原则：单一职责、描述清晰、参数强约束、结果结构化、幂等、超时、审计、最小权限。

### 4.7 Agent 和 ChatBot 区别

> ChatBot 通常是一次输入一次输出；Agent 围绕目标可以多轮决策、调用工具、观察结果并调整下一步。真正差异不只是“有工具”，而是模型拥有有限决策权，同时 Runtime 对动作进行治理。

### 4.8 ReAct 难点

> ReAct 难点不是 while 循环，而是模型协议遵循、停止条件、重复动作、工具失败、上下文增长、Token 成本和轨迹复现。生产上要通过统一执行预算、无进展检测、工具幂等和 Trace 控制风险。

### 4.9 幻觉为什么产生，怎么治理

原因包括训练知识缺失、问题歧义、错误检索、上下文冲突、模型被要求强行回答和工具结果误读。

治理手段：

- RAG 和可靠工具提供事实。
- 引用和 Groundedness 评估。
- 无答案检测和明确拒答。
- 结构化输出和业务规则校验。
- 高风险动作 Human-in-the-loop。
- 不能仅靠 System Prompt 保证事实正确。

### 4.10 RAG 怎么评估

检索层：Recall@K、Precision@K、MRR、NDCG、引用命中率、各通道召回数和 P95 延迟。

生成层：答案相关性、Groundedness、引用正确性、完整性、无答案拒答率。

Agent 层：任务成功率、Tool Call 准确率、参数准确率、平均轮数、重复动作率、Token 成本、轨迹成功率。

> 先建立 Golden Dataset，再改 Chunk、TopK、阈值或 Reranker；没有评估集时调参数主要靠感觉。

### 4.11 MCP 是什么

> MCP 是 Model Context Protocol，用统一协议向 AI 应用暴露工具、资源和 Prompt，降低模型客户端与外部系统的集成复杂度。它解决连接标准化，不自动解决安全；生产仍需身份透传、工具白名单、超时、租户隔离和审计。

当前项目的工具注册思想类似，但不能宣称已经实现标准 MCP Server。

### 4.12 Prompt Injection 怎么防

> 用户输入、网页和知识库内容都属于不可信数据，不能让文档里的“忽略之前规则”覆盖系统权限。防御重点不是追加一句 Prompt，而是工具最小权限、读写隔离、参数校验、敏感动作审批、出站 URL 防护、租户隔离和完整审计。

### 4.13 模型失败与成本治理

> 401/403/404 通常是认证、权限或配置问题，不做无意义重试；429 和 5xx 可以指数退避并加入抖动。连续失败应触发熔断。调用前检查配额，调用后记录 prompt/completion Token、耗时和成功率。

当前项目有 Token 配额和记账，没有人民币成本核算，也没有基于成本自动切模型。

### 4.14 AI Native Workflow 怎么理解

> AI Native Workflow 不是在 IDE 里加一个聊天框，而是把需求上下文、项目知识、任务拆解、代码生成、测试、Review、文档和反馈沉淀串成可验证闭环。AI 提高产出速度，人负责目标、边界、验收和责任。

## 5. Java 基础、并发与 JVM 八股

### 5.1 HashMap 原理

> Java 8 的 HashMap 是数组 + 链表 + 红黑树。Key 的 hash 经过扰动后定位桶；冲突先形成链表，桶中元素达到阈值且数组容量足够时树化。默认负载因子 0.75，是空间和冲突概率的折中。它不是线程安全的。

追问：为什么容量通常是 2 的幂？因为可以用 `(n - 1) & hash` 高效取模，同时让扩容后元素只留在原位置或移动旧容量距离。

### 5.2 equals 和 hashCode

> equals 相等的对象必须有相同 hashCode，否则 HashMap/HashSet 可能放到不同桶；hashCode 相同不代表 equals 一定相等。作为 Key 的字段最好不可变，否则放入后修改可能无法再次找到。

### 5.3 ConcurrentHashMap

> Java 8 使用数组、链表/红黑树以及 CAS + synchronized 控制并发。读操作通常无锁，桶初始化等操作用 CAS，桶冲突更新锁定桶头节点，避免对整个 Map 加锁。

复合操作使用 `computeIfAbsent`、`putIfAbsent` 等原子 API，不能用“先 get 再 put”假设原子性。

### 5.4 ArrayList 和 LinkedList

- ArrayList 连续数组，随机访问快，尾部追加均摊 O(1)，中间插入需要移动元素。
- LinkedList 节点分散，定位元素仍需 O(n)，缓存局部性差，工程中并不因为“插入 O(1)”就一定更快。

### 5.5 String 为什么不可变

> 不可变使字符串池、安全校验、Hash 缓存和并发共享更可靠。拼接次数多时用 StringBuilder；跨线程同步修改才考虑 StringBuffer，但通常更推荐局部 StringBuilder。

### 5.6 JMM、可见性、原子性、有序性

> Java 内存模型规定线程如何通过主内存交互。并发问题主要是可见性、原子性和有序性。`volatile` 保证可见性和一定的有序性，但 `i++` 仍不是原子操作。

### 5.7 synchronized、volatile、ReentrantLock

- `volatile`：状态标记、单写多读，不适合复合原子操作。
- `synchronized`：语法级互斥，自动释放锁，适合普通临界区。
- `ReentrantLock`：支持可中断、超时、公平锁和多个 Condition，必须在 finally 解锁。

选择依据不是谁“更高级”，而是是否需要高级锁能力。

### 5.8 CAS、ABA、AQS

> CAS 比较内存值是否仍等于期望值，相等才更新，避免阻塞；高竞争下会自旋消耗 CPU，并有 ABA 问题，可通过版本号解决。AQS 用一个 state 和等待队列抽象锁及同步器，ReentrantLock、Semaphore、CountDownLatch 都建立在它之上。

### 5.9 线程池七个参数和拒绝策略

核心参数：corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler。

执行顺序：

```text
核心线程未满 -> 创建核心线程
核心满       -> 进入队列
队列满       -> 创建非核心线程直到 max
线程和队列都满 -> 拒绝策略
```

生产建议：使用有界队列、自定义线程名、明确拒绝策略和监控；线程数根据 CPU 密集或 IO 等待比例压测确定，不能直接套公式。

### 5.10 ThreadLocal

> ThreadLocal 为每个线程保存独立变量，常用于请求上下文。线程池会复用线程，如果不 remove，旧值可能污染下一个请求并造成内存占用，所以必须 try/finally 清理；异步线程还需要显式传递上下文。

### 5.11 CompletableFuture 注意点

> 适合编排异步任务，但要显式指定业务线程池，避免阻塞公共 ForkJoinPool；区分串行依赖、并行汇合和异常处理；设置超时，并确保安全上下文、MDC、租户信息正确传播。

### 5.12 JVM 内存区域

- 堆：对象实例，GC 主要管理区域。
- 虚拟机栈：栈帧、局部变量、操作数栈，线程私有。
- 方法区/元空间：类元数据、常量等。
- 程序计数器：当前线程执行位置。
- 本地方法栈和直接内存：JNI、NIO 等场景。

### 5.13 对象何时可回收

> JVM 使用可达性分析，从 GC Roots 出发无法到达的对象才可能回收。GC Roots 包括栈中的引用、静态字段、JNI 引用和运行中的线程等。引用计数无法解决循环引用，因此 JVM 不使用它作为主要判断方式。

### 5.14 常见 GC 和 G1

> G1 把堆划分为 Region，按收益优先回收垃圾多的区域，目标是可预测停顿；它仍可能因分配速度过快、晋升失败、Humongous 对象或并发标记跟不上而发生 Full GC。

回答调优原则：先定位对象和流量原因，再考虑堆大小、Region、停顿目标等参数，不能只靠扩大堆。

### 5.15 类加载和双亲委派

> 加载器收到请求后先委托父加载器，父加载器无法加载才自己尝试。它避免核心类被重复或恶意替换。类加载过程包括加载、验证、准备、解析、初始化。

## 6. Spring 八股

### 6.1 IoC 和 AOP

> IoC 把对象创建、依赖和生命周期交给容器；AOP 通过代理把事务、日志、权限等横切逻辑从业务代码中分离。Spring AOP 常用 JDK 动态代理或 CGLIB。

### 6.2 Bean 生命周期

```text
实例化
 -> 属性注入
 -> Aware 回调
 -> BeanPostProcessor before
 -> 初始化方法
 -> BeanPostProcessor after（可能生成代理）
 -> 使用
 -> 销毁回调
```

### 6.3 Spring 事务为什么会失效

常见原因：

- 同类方法自调用绕过代理。
- 方法不是可代理的 public 方法。
- 异常被捕获但没有继续抛出。
- 抛出受检异常但未配置 rollbackFor。
- 新线程不继承原线程事务。
- 数据库表或存储引擎不支持事务。

### 6.4 事务传播

- REQUIRED：有事务就加入，没有就新建，最常用。
- REQUIRES_NEW：挂起外层事务，创建独立事务，适合必须独立提交的审计等场景，但要注意连接数。
- NESTED：基于保存点嵌套，依赖数据库支持。

### 6.5 Spring Boot 自动配置

> 自动配置根据 classpath、配置属性和 Bean 是否存在，通过条件注解注册默认 Bean。它不是“自动扫描一切”，而是约定加条件装配；业务可以通过自定义 Bean 覆盖默认实现。

### 6.6 Spring MVC 请求链路

```text
请求 -> DispatcherServlet -> HandlerMapping -> HandlerAdapter
    -> Controller -> Service -> 返回值处理/消息转换 -> Response
```

Filter 属于 Servlet 层，Interceptor 属于 Spring MVC 层，AOP 面向方法调用。

## 7. MySQL 八股

### 7.1 为什么使用 B+ 树

> B+ 树分支多、高度低，减少磁盘 IO；非叶子节点只保存索引，叶子节点保存数据或主键并通过链表连接，范围查询效率高。Hash 索引不适合范围和排序。

### 7.2 聚簇索引和二级索引

> InnoDB 主键索引叶子节点保存整行数据；二级索引叶子节点保存索引列和主键。通过二级索引查其他列可能需要回表。覆盖索引让查询字段都在索引中，可避免回表。

### 7.3 联合索引和最左前缀

> 联合索引按照从左到右排序。查询能否使用后续列，取决于前面列是否提供有序范围。范围条件之后的列通常难以继续用于定位，但仍可能用于索引下推过滤。

### 7.4 常见索引失效/效果差

- 对索引列做函数或隐式类型转换。
- `like '%xxx'` 前缀不确定。
- 选择性太差，优化器判断全表扫描更便宜。
- 联合索引没有遵守有效前缀。
- `or` 中部分条件没有可用索引。

最终以 `EXPLAIN` 和真实数据分布为准，不要机械背“必然失效”。

### 7.5 Explain 重点看什么

> 看访问类型、possible_keys/key、rows、filtered、Extra。重点关注全表扫描、预估扫描行数过大、临时表、文件排序和回表；再结合慢日志和实际执行时间判断。

### 7.6 MVCC 和隔离级别

> MVCC 通过隐藏事务字段、Undo Log 和 Read View 提供一致性读。读已提交每次快照读生成新 Read View；可重复读通常在事务第一次快照读时建立 Read View，因此同一事务多次快照读结果稳定。

当前读如 `select ... for update` 会读取最新版本并加锁，不等同于快照读。

### 7.7 锁和死锁

> InnoDB 有记录锁、间隙锁和 Next-Key Lock。死锁常由不同事务以不同顺序获取资源造成。解决方式包括统一加锁顺序、缩小事务、建立合适索引、减少锁范围，并对死锁回滚做有限重试。

### 7.8 深分页怎么优化

> `limit offset,size` 会扫描并丢弃前面的记录。可以使用基于有序唯一键的 Seek Pagination，例如 `where id > lastId order by id limit n`；复杂场景可先用覆盖索引取主键，再回表关联。

### 7.9 幂等怎么做

> 优先使用业务唯一键和数据库唯一索引作为最终防线；入口可使用请求号去重，消费端记录处理状态，状态变更采用条件更新或版本号。Redis 去重可以减压，但不应替代数据库最终约束。

## 8. Redis 与 Kafka 八股

### 8.1 Redis 常用结构和场景

- String：缓存、计数、简单锁。
- Hash：对象字段。
- List：简单队列，但复杂消息系统优先 MQ。
- Set：去重、关系集合。
- ZSet：排行榜、延迟任务索引。
- Bitmap/HyperLogLog：状态位、近似基数统计。

### 8.2 缓存穿透、击穿、雪崩

- 穿透：查询不存在数据。空值缓存、布隆过滤器、参数校验。
- 击穿：热点 Key 过期，大量请求打数据库。逻辑过期、互斥重建、热点预热。
- 雪崩：大量 Key 同时过期或 Redis 故障。随机 TTL、多级缓存、限流降级、高可用。

### 8.3 数据库和缓存一致性

常用 Cache Aside：

```text
读：先缓存，未命中查数据库并回填。
写：先更新数据库，再删除缓存。
```

删除失败可通过重试、消息队列、订阅 Binlog 或延迟双删提高最终一致性。不要宣称普通双写能提供强一致。

### 8.4 Redis 分布式锁

> 使用唯一请求值和带 TTL 的原子加锁；解锁必须通过 Lua 比较持有者再删除。业务执行时间可能超过 TTL 时需要续期；仍需考虑进程暂停、主从切换和下游幂等，锁不是一致性的唯一防线。

### 8.5 Kafka 架构和顺序性

> Topic 被拆成 Partition，每个 Partition 是追加日志；同一消费组内，一个 Partition 同时只由一个消费者处理。因此 Kafka 只保证单 Partition 内顺序。需要局部有序时，把相同业务 Key 路由到同一 Partition。

### 8.6 Kafka 如何减少丢失

- Producer 使用合适的 `acks`、重试和幂等生产者。
- Broker 配置足够副本和最小同步副本。
- Consumer 处理成功后再提交 Offset。
- 关键业务做数据对账，不能只相信 MQ 配置。

### 8.7 Kafka 重复消费和幂等

> 消费成功但 Offset 未提交时可能重复投递，因此业务侧必须幂等。常用业务唯一键、唯一索引、处理记录表或状态机条件更新。Exactly Once 不等于跨外部数据库天然全局 exactly-once。

### 8.8 Kafka 消息积压

排查：生产速度、消费耗时、Partition 数、消费者数量、外部依赖、失败重试和大消息。

处理：先止损限流；优化单条处理和批量；在 Partition 足够的情况下增加消费者；隔离失败消息；必要时临时扩容并做最终对账。

## 9. 分布式、高并发、高可用八股

### 9.1 CAP 和 BASE

> 网络分区不可避免时，系统需要在一致性和可用性之间取舍。CAP 不是平时永远三选二，而是在发生分区时的选择。BASE 通过基本可用、软状态和最终一致性换取系统整体可用。

### 9.2 如何设计高并发接口

```text
先定义容量目标和一致性要求
 -> 无状态服务水平扩展
 -> 缓存和数据预计算
 -> MQ 削峰与异步化
 -> 数据库索引、分片或读写扩展
 -> 限流、熔断、降级、超时
 -> 幂等和最终一致性
 -> 指标、压测、容量预案
```

不要一上来就回答“Redis + MQ”，先说明流量、读写比、热点和一致性要求。

### 9.3 限流算法

- 固定窗口：简单但边界可能突发。
- 滑动窗口：更平滑，统计成本更高。
- 漏桶：稳定速率输出，适合整形。
- 令牌桶：允许一定突发，常用于接口限流。

限流维度可以是用户、租户、IP、接口、模型、工具和总资源池。

### 9.4 超时、重试、熔断、降级关系

> 超时限制单次等待；重试应只针对短暂且幂等的失败，并有次数和总时间预算；熔断防止持续故障拖垮调用方；降级在核心依赖不可用时返回缓存、规则结果或明确错误。无脑重试会放大故障。

### 9.5 分布式事务怎么选

- 强一致、短事务且基础设施支持：可考虑 XA，但成本高。
- 跨服务业务：本地事务 + Outbox/事务消息 + 幂等消费 + 补偿，通常更实用。
- 长业务流程：Saga，每步有补偿动作。
- TCC：资源预留明确但侵入性高。

选择前先问业务能否接受最终一致，而不是默认上复杂框架。

### 9.6 高可用设计

- 多实例、无状态、健康检查和自动摘除。
- 数据库、Redis、MQ 副本和故障转移。
- 依赖超时、隔离、熔断和降级。
- 配置中心、灰度发布和快速回滚。
- 全链路指标、日志、Trace 和告警。
- 容量评估、压测、故障演练和恢复预案。

高可用不等于“永不失败”，而是控制故障范围并快速恢复。

### 9.7 一致性哈希

> 把节点和 Key 映射到环上，节点变化时只迁移相邻区间的数据，减少普通取模导致的大规模重映射；虚拟节点用于改善数据倾斜。

### 9.8 接口防重复提交

> 客户端携带唯一请求号，服务端建立幂等记录；数据库唯一索引作为最终防线；状态更新使用条件或版本号；返回结果可以按请求号复用。仅用前端按钮置灰不可靠。

## 10. 岗位相关系统设计题

### 10.1 设计一个企业 AI Agent / 知识库平台

先问清楚：用户规模、文档量、更新频率、延迟目标、是否多租户、是否需要写操作、允许成本和准确率要求。

总体架构：

```text
API Gateway / Auth / Rate Limit
  -> Agent Runtime
       -> Router / Orchestrator / ReAct
       -> Tool Gateway（权限、超时、审计）
       -> Model Gateway（配额、重试、熔断、模型配置）
       -> RAG Service（解析、混合召回、重排、引用）
       -> Memory Service
  -> MySQL / Redis / Milvus / Elasticsearch / Object Storage
  -> Trace / Metrics / Audit / Evaluation
```

必须主动提到：

- 多租户和知识权限过滤必须在召回前生效。

- 模型和工具分别设置超时、并发、Token 和费用预算。
- 写操作 Human-in-the-loop，读写工具隔离。
- 评估最终答案和中间执行轨迹。

### 10.2 设计浏览器矩阵产品的服务端平台

不要假装知道对方内部架构。先澄清产品形态、地区、DAU、读写比、账号体系、内容来源和一致性要求。

可展开的模块：

```text
统一网关、账号与设备体系
配置/实验/灰度平台
内容聚合和推荐接口
小说、音乐等业务域服务
消息、任务和运营后台
对象存储 + CDN
日志、指标、Trace、风控与审计
```

出海场景重点：

- 多地域部署、DNS/GSLB/CDN、跨地域容灾。
- 静态配置和内容边缘缓存，减少跨洲延迟。
- 用户、设备、地区和实验维度的配置隔离。
- 多语言、时区、货币和地域配置。
- 数据驻留、隐私合规和最小化采集。
- 跨区域数据通常追求最终一致，账号和支付等核心链路按业务选择更强一致。

### 10.3 设计 AI 研发 Workflow

```text
需求/Issue
 -> 自动加载项目知识和编码规范
 -> AI 生成任务拆分和风险点
 -> 人确认设计边界
 -> AI 辅助编码
 -> 自动单测、静态检查、依赖和安全扫描
 -> AI Review + 人工 Review
 -> 灰度/发布
 -> 线上反馈沉淀到评估集和知识库
```

关键判断：

> AI Workflow 的指标不是生成了多少代码，而是 Lead Time、Review 返工率、缺陷逃逸率、测试覆盖、知识复用率和开发者采纳率。高风险变更必须保留人工审批和可追溯记录。

## 11. 行为题与反问

### 11.1 如何体现主人翁意识

> 我理解主人翁意识不是无限接活，而是对结果负责：主动澄清目标，提前暴露风险，推动依赖方给出结论；上线前准备监控和回滚，上线后验证指标；出现问题时先止损和定位，再复盘机制，而不是只修当前数据。

使用“流式 ReAct 缺少 Trace”故事证明你会主动发现系统缺口。

### 11.2 与同事意见不一致

> 先对齐共同目标和评价指标，再把争论从偏好转成证据。低成本时做小规模验证；存在上线风险时明确记录方案、收益、风险和回滚条件。最终决策确定后积极执行，同时保留监控验证假设。

### 11.3 任务时间紧怎么办

> 先识别不可妥协的正确性和安全边界，再拆 MVP、可延后项和风险项；尽早同步依赖和时间预期；用灰度、开关和监控降低上线风险。抗压不是沉默加班，而是在压力下保持优先级和信息透明。

### 11.4 AI 生成的代码是不是你写的

> 我会使用 AI 做代码检索、方案对比、初版实现和测试，但需求拆解、架构边界、验收标准和故障定位由我负责。模型只说要调用工具但没发 Tool Call、流式路径缺少 Trace，都是我从运行行为定位并完善的。AI 提高速度，但最终判断、验证和责任在我。

### 11.5 反问：技术负责人优先选择两个

> 我看到岗位同时涉及浏览器矩阵产品的服务端建设，以及 Agent、知识库和研发 Workflow。团队未来半年到一年最希望通过 AI 解决的核心问题是什么？目前更侧重用户侧 Agent，还是内部研发提效？

> 团队评价 Agent 落地主要看哪些指标？目前最大的瓶颈是在知识质量、模型稳定性、成本延迟，还是业务流程接入？

> 出海浏览器和小说、音乐等矩阵产品，在服务端高可用方面当前最有挑战的是全球化部署、流量波动、数据一致性还是合规隔离？

### 11.6 反问：直属领导

> 如果我加入，前三个月最希望我解决什么问题？您认为这个岗位表现比较好的同学，最核心的能力和产出是什么？

### 11.7 面试结束收口

> 通过今天的交流，我对这个岗位的方向更明确了。它既需要服务端基本功，也需要持续探索 Agent 和 AI Workflow，这正是我希望长期积累的方向。我也希望进入真实业务场景，对系统稳定性和业务指标负责，而不只是做一个 AI Demo。

不要在技术面优先问：公司做什么、有没有人带、平时是否经常加班、使用哪个大模型。薪酬福利放到 HR 阶段沟通。

## 12. 最后一页速记

### 12.1 十句话

1. 我的长期方向是 Java 服务端 + AI 应用工程。
2. Agent 是模型驱动的受控执行系统，不是聊天套壳。
3. Orchestrator 管任务和专家，ReAct 管开放式动态执行。
4. 外层确定性编排，内层概率性执行；高风险动作必须审批。
5. 8 轮是安全上限，不是最佳值；生产要用多维执行预算。
6. 向量解决语义，BM25 解决精确词，RRF 按排名融合。
7. 原文/Document AST 是事实源，Chunk 和向量只是索引。
8. RAG 质量必须靠 Golden Dataset 和检索/生成分层指标评估。
9. 模型调用要有超时、有限重试、熔断、配额和 Trace。
10. AI 提高研发速度，人负责目标、边界、验收和责任。

### 12.2 服务端万能检查表

```text
容量：QPS、数据量、P95/P99、峰值
正确性：幂等、事务、一致性、对账
稳定性：超时、重试、限流、熔断、降级
性能：缓存、异步、批量、索引、线程池
安全：认证、权限、租户、审计、数据合规
发布：灰度、开关、回滚、兼容性
观测：日志、指标、Trace、告警
```

### 12.3 面试前最后动作

1. 自我介绍脱稿说两遍。
2. 三个项目故事各说一遍。
3. ReAct、Orchestrator、RAG 各用一分钟说一遍。
4. 线程池、JVM、MySQL 索引、Redis 缓存、Kafka 幂等各过一遍。
5. 选定两个反问，不要临场现想。
6. 停止输入新知识，保持语速和状态。
