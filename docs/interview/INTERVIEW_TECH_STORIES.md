## 0. 开场总纲：你的差异化在哪

大多数候选人简历写"做过 agent"，其实只是调了一次 function calling demo。你的差异化有两层：

1. **广度是生产级**：RAG 全链路 + 记忆分层 + 熔断降级 + token 记账 + 多租户 + 流式 + 可观测，不是玩具。
2. **你有"自主 vs 编排"的批判性认知**（见故事 #2）——这是 3-5 年经验的信号，背不出来。

一句话定位（被问"介绍下你的项目"时）：
> "它不是调一次大模型，而是一套企业数据分析的 Agent Runtime。我做的过程中最大的收获，是理解了 **agent 的自主性和工程可控性之间的根本张力**——我两种形态都实现过，可以展开讲。"

最后这句话是钩子，面试官大概率会追问，你就把控了节奏。

## 总纲故事 · "编排优先架构"的冰山（最高级的一条，统领其他）

> 这是把所有具体踩坑（光说不练、假流式、分类器边界、上下文污染）收敛成**一个根因 + 一个演进方向**的主线故事。能讲好这条，等于证明你有架构师级判断力，而不只是"会用框架"。

**怎么引出**（面试聊到项目难点 / 架构反思时）
> "我这个 agent 最大的收获不是某个功能，而是发现它的架构有个系统性问题——我一开始以为是几个独立 bug，后来意识到是**同一个架构姿态长出来的许多张脸**。"

**冰山：水面上是症状，水面下是同一个根**
- 水面（已发现的症状）：① 中途一句"你好"也触发完整 ReAct 循环（7秒/3000+token）；② 模型"光说不练"（说要调工具却不发 function call）；③ 一开始是"假流式"（先同步跑完再一次性吐事件）。
- 水面下（系统性问题，同源）：
  - **决策权错位**：确定性分类器用关键词替模型判简单/复杂；快路闸门凭分类剥离工具；规划器在模型思考前预排步骤。
  - **各层不协同**：并行预检空跑、结果不传给 ReAct 循环 → 模型又搜一遍（冗余）；预检的"没结果"上下文反而诱发模型写旁白（光说不练的根）。
  - **上下文污染**：RAG 无差别注入（给"你好"塞进无关文档）；全量会话历史无差别加载 → 模型过度联想无关话题。

**根因（一句话）**
> "根子是**编排优先（orchestration-first）**：系统是按'模型不可靠、要用一堆确定性层去帮它管它'的假设建的。每层单独看都有道理，合起来就**把决策权层层抽走、各层还不共享状态**。但我实测发现——**强模型（pro）自己就能多步规划、自己判断该不该调工具，这层脚手架早已是负债，制造的问题比解决的多**。"

**演进方向（两条路，按场景选）**
> "有两条路：① **模型优先**——砍掉确定性层，模型驱动 + 工具 + 必要护栏（我做的'自主模式开关''工具决策轮非流式'就是往这挪）；② **保留编排但让各层共享状态、协同**（LangGraph 那种有状态编排）。"

**升华到企业落地（这段最能体现高度）**
> "那企业 agent 到底该编排还是信任模型？我的结论是**正确的轴不是'信不信模型'，是'风险高不高'**：对**推理**（想什么、查什么、怎么拆步骤）信任模型；对**高风险动作**（转账、发邮件、删库、改价、合规决策）做编排（权限/审批/审计）。**我这个项目的错恰恰是编排了'推理'、却没重点管'危险动作'——刹车装错了地方**。企业 agent 的甜点区是'带刹车的自主'：模型自主驱动推理，编排只管危险动作。一句话——**编排动作，不要编排推理（Orchestrate actions, not reasoning）**。"

**为什么这条值钱**：它证明你能看着真实代码库诊断出"这是为弱模型设计的编排优先架构，在强模型时代变成负债"，还能给出演进路径和企业落地判断——这是背八股背不出来的。

## 故事 #1 · Agent 内核：ReAct 循环 + Function Calling

**会被问**
- ReAct 是什么？跟普通调模型有什么区别？
- function calling / tool use 底层怎么工作的？
- 循环什么时候停？会不会死循环？

**你的素材**
- `ReActLoopRunner.run() / runStreaming()`：一个 while 循环，最多 8 轮（`MAX_ITERATIONS=8`）。
- 每轮：把 `[系统提示 + 工具规格 + 消息历史]` 发给模型 → 模型回 AiMessage（要么带 tool call，要么是最终答案）→ `ReActResponseParser` 解析 → 有 tool call 就 `AgentToolInvoker` 执行、结果塞回 messages、继续；没有就收敛。
- 工具规格不是手写 JSON：`AgentToolInvoker` 用 LangChain4j 的 `ToolSpecifications.toolSpecificationFrom(method)` 从 `@Tool` 注解**反射自动生成**，新增工具只加一个注解方法。

**讲出取舍（加分）**
> "停止条件我用了两道：模型主动不再调工具就收敛，加一个 8 轮硬上限兜底防死循环。达到上限时我不是直接报错，而是 `MAX_ITERATION_ANSWER_PREFIX` 把已获得的中间结果整合给用户做保守结论——因为 agent 最怕的不是答不全，是无限烧 token。"

**追问陷阱**
- "8 轮怎么定的？"→ 经验值，数据分析任务很少超过 5 步；可配置。诚实说是拍的，但解释了依据。
- "模型不支持 function calling 怎么办？"→ 我还有文本协议解析兜底（`[CALL:工具名(参数)]` 这种 prompt 约定，见 ReActAgent 的 SYSTEM_PROMPT）。

## 故事 #2 · 杀手锏：自主 Agent vs 编排式（你的最强项）

**会被问**
- 你怎么理解 agent 的"自主性"？
- 多 agent 编排和单 agent 有什么区别？什么时候用哪个？
- 你这个 agent 是模型在做决策还是你代码在做决策？

**你的素材（真实踩坑）**
- 我最初的设计有 6 层前置：路由 → RAG → `TaskComplexityClassifier`（关键词分类）→ 快慢路闸门 → `TaskPlanner`（预规划）→ 并行预检 → 才进 ReAct 循环。
- **我后来意识到一个严重问题**：模型直到第 7 步才被允许做第一个决定，前 6 层全是 Java 代码替它决策。最致命的是快路闸门（`ReActAgent.executeStreaming`）——一旦关键词判定"简单问题"，直接走 `fastAnswerService`，**连工具清单都不传给模型**，模型只能凭训练记忆硬答。
- 这本质上是**用工程确定性换掉了 agent 的核心**。

**讲出取舍（这段背下来）**
> "这让我理解了一条光谱：左边是工作流编排（Dify、Coze、Copilot Studio），流程人画好、LLM 只填空，可控可审计；右边是自主 agent（Claude Code、Codex），决策权全交模型，灵活但 token 不可控、不可审计。
>
> 企业产品大多偏左，因为合规和确定性比灵活更重要；但前沿在往'带刹车的自主'走（LangGraph 那种主干自主 + 高风险动作人工审批）。
>
> 我两种都实现了：编排版适合企业落地，自主版才是真正的 agent。我现在会**有意识地**根据场景选择牺牲多少自主性，而不是默认框死。"

**为什么这条最值钱**：它同时证明你懂原理、懂行业、懂取舍、还能反思自己的设计。面试官最想招的就是这种人。

**追问陷阱**
- "那你最终选哪个？"→ 看场景。金融客服我选编排（可审计）；开发者工具我选自主（灵活）。给答案，但先给判断框架。
- "怎么给自主 agent 加刹车？"→ human-in-the-loop 审批、工具权限边界、token 配额、执行追踪（我项目里 `agent_execution_trace` 就是干这个的）。

## 故事 #3 · RAG 全链路（你的王牌，必被深挖）

**会被问**
- 你的 RAG 怎么做的？为什么不是纯向量检索？
- 召回不准怎么调？
- chunk 怎么切？rerank 解决什么问题？

**你的素材**
- 不是单一向量检索，是**融合管道**：全文检索 + 向量检索 + 父上下文 + 重排（rerank）+ 压缩 + 质量评估。
- 全文召回固定使用 Elasticsearch BM25，向量召回使用 Milvus；两路候选通过 RRF 融合。
- ES 索引使用显式 Mapping 和版本化索引名，避免动态 Mapping 导致租户/来源 `term` 过滤零命中。
- 向量库 Milvus，collection `data_agent_vectors`。

**讲出取舍（加分）**
> "纯向量检索的问题是**对精确关键词、专有名词、编号不敏感**——'查订单 SO-2024-001'这种向量召回经常漂。所以我用混合检索：全文负责精确匹配，向量负责语义相似，两路融合。
>
> rerank 是因为**召回阶段为了高 recall 会放宽，Top20 里会混入不相关片段**。我后来接入了外部 Cross-Encoder，把 query 和每个 Chunk 成对打分，再取 Top6；返回索引会做越界、重复、缺失和非法分数校验。因为它增加了网络延迟和外部依赖，我加了超时、有限重试、熔断和规则 fallback，Trace 会记录实际 Provider、模型、耗时和降级原因。代码接入不等于效果提升，我还要用相同 RRF Top20 对比规则与 Cross-Encoder 的 MRR、NDCG、Hit@6 和 P95，实测完成前不会虚报指标。
>
> 压缩是为了**省上下文窗口**——召回 10 段但不是每段都全文有用，压缩成精炼上下文再喂模型。"

**追问陷阱**
- "chunk size 怎么定？"→ 要有答案：太大噪声多、太小丢上下文，我用父子结构（小 chunk 检索、父块给上下文）。这就是"父上下文"那一环。
- "怎么评估 RAG 好不好？"→ **这是常见的洞**，见故事 #10。提前准备：召回率、答案 groundedness、有没有引用来源。我项目里有"质量评估"环节可以讲。

**真实踩坑讲法**
> "第一版为了本地可运行，用 JPA LIKE 冒充全文兜底，但它查询时扫描业务表、重新切 Chunk，分数也不是 BM25，数据一多延迟和结果都不可控。我后来删掉这个伪降级，让 ES 成为唯一全文通道。切换时又发现动态 Mapping 会把 tenantId 映射成 text，而查询用 term 精确过滤，表现就是索引有数据但召回为 0。所以我把索引升级到 v2，显式规定 keyword/text 字段，并让写索引失败直接暴露，避免系统显示入库成功但实际只有 Milvus 有数据。"

## 故事 #4 · 记忆系统（分层是关键词）

**会被问**
- agent 的记忆怎么做？跟直接塞历史对话有什么区别？
- 上下文窗口满了怎么办？
- 长期记忆怎么存、怎么取？

**你的素材**
- 分层：working（工作记忆，单次任务内）/ short-term（短期，近期会话）/ long-term（长期，跨会话沉淀）/ user_profile（用户画像）。
- 持久化表 `memory_entry`、`user_profile`。
- 有压缩、衰减（decay）、保留（retention）策略。
- 模型压缩默认关闭（`MEMORY_MODEL_COMPRESSION_ENABLED=false`）。

**讲出取舍（加分）**
> "直接塞全部历史的问题是**上下文窗口爆炸 + token 成本线性增长 + 远期信息稀释**。所以分层：工作记忆只在单次推理循环里活着，短期记忆是滑动窗口，长期记忆是经过提炼的沉淀。
>
> 一个我特意做的取舍：**模型压缩默认关掉**。用 LLM 压缩记忆听起来高级，但它增加延迟、烧 token、还可能压丢关键信息。我默认用规则化的衰减+保留，只在必要时开模型压缩——**不是所有环节都该上 LLM**。"

**追问陷阱**
- "怎么决定什么进长期记忆？"→ 重要性打分 + 衰减，高频/高价值的留存。
- "记忆检索和 RAG 检索什么关系？"→ 都是向量召回，但记忆是"关于这个用户/会话"的，RAG 是"关于企业知识"的，prompt 里分两个 section（我有 `MemoryContextPromptFormatter`）。

## 故事 #5 · 向量与 Embedding（容易被问维度坑）

**会被问**
- embedding 模型和部署方式怎么选？
- 向量维度改了会怎样？
- Milvus 启动慢/卡住怎么处理？

**你的素材**
- 当前统一走 OpenAI-compatible Embedding 服务，Java 业务进程不加载模型权重；服务可独立部署、扩缩容和替换模型。
- 旧配置曾同时在 `app.embedding.dimension` 和 `milvus.dimension` 维护维度，而且 API 默认模型常见输出 1024 维，旧默认仍是 384，存在双事实源和延迟失败风险。
- 现在用 `EmbeddingProfile` 统一固定 provider `api`、modelId、indexVersion、dimension、normalize 和 metric；启动真实探测维度，每次 embed 后重复校验。
- Milvus 物理 Collection 名携带 provider、模型、维度、Metric 和索引版本；新向量元数据也保存这五项身份信息。
- `MilvusEmbeddingStore` 首次 add/search 才创建，已有 Collection 的 load 请求使用异步模式，不阻塞等待完整加载。

**讲出取舍（加分）**
> "我最后把 Embedding 收敛成 **API-only**，不是不要向量，而是把推理和 Java 业务进程解耦。好处是模型服务能独立使用 GPU、扩缩容和升级，业务 JVM 不再背模型权重；代价是增加网络依赖，所以 Base URL、模型名和维度必须显式配置，启动先做真实探测。服务失败直接暴露，不静默回退，因为临时换模型会让查询向量和库内向量不在同一空间，表面可用但召回结果已经不可信。
>
> 真正发现的坑是**Embedding 和 Milvus 各维护一份维度**：API 模型名换成 `bge-large-zh-v1.5` 后，如果仍沿用 384，错误可能到第一次写向量才出现。我把它收敛成一个 Embedding Profile，启动时真实请求一条探测向量，错误信息带 modelId、期望维度和实际维度；每次 embed 后也再校验一次。
>
> 只校验维度还不够，同维度的不同模型也不是同一个向量空间。所以物理 Collection 名会带 provider、模型、维度、Metric 和 indexVersion。换模型时提升版本并重建，不自动删除旧 Collection。代价是启动多一次 Embedding 调用、迁移期多占存储，但换来错误前置和版本可回退。这个改造解决的是索引兼容性，还没有黄金集实测，所以我不会声称 Recall 已经提升。"

**追问陷阱**
- "向量维度为什么不能写死为 384 或 1536？"→ 维度由实际服务模型决定，必须显式配置并用真实输出探测；维度更高不等于业务 Recall 一定更好。
- "Collection 名为什么还要带模型，维度一样不就行？"→ 同维度只代表数组长度相同，不代表向量空间相同；不同模型的向量不能直接比较。
- "启动探测有什么代价？"→ 多一次 API 调用和少量启动延迟，换取配置错误在接流量前暴露。

## 故事 #6 · 模型接入：重试、熔断、降级、Token 治理（生产化信号）

**会被问**
- 模型调用失败怎么办？
- 怎么控制成本？
- 多模型/多厂商怎么管理？

**你的素材**
- `ModelRetryExecutor`：**401/403/404 不重试**（鉴权/路径错，重试无意义），429/5xx 才重试——区分可恢复和不可恢复错误。
- 熔断：`ModelHttpClient` 层面。
- Token 治理：`TokenQuotaGuard`（配额拦截）+ `TokenMonitor`（用量监控）+ `TokenUsageRecorder`（记账，优先用厂商返回的真实 usage）。
- 多厂商：OpenAI 兼容协议 + Kimi 适配（别名归一化，`kimi-2.6` → `kimi-for-coding`）。
- `ModelConfigService` 保证同租户单一默认模型，变更发 `ModelConfigChangeEvent` 清缓存。

**讲出取舍（加分）**
> "重试最忌讳无脑重试。401 是 key 错了，你重试 3 次还是 401，纯浪费还拖慢用户。所以我按状态码分类：不可恢复的（4xx 鉴权类）立即失败，可恢复的（429 限流、5xx 服务端）才退避重试。
>
> 成本上我做了三道：调用前配额拦截、调用中记账用厂商真实 usage（不是自己估 token，估不准）、配额超了直接拦。
>
> 模型配置变更我用事件驱动清缓存，而不是让别人直接写缓存——否则缓存和 DB 不一致，下次还用老模型。"

**追问陷阱**
- "熔断和重试什么关系？"→ 重试是单次调用内的，熔断是跨调用的：连续失败就短路一段时间，别让下游雪崩。

**实测案例：模型能力直接决定 agent 自主性（flash vs pro，我亲手跑过）**
> "我用 deepseek 的 flash 版和 pro 版跑同一个 agent、同一个问题（'知识库里有没有关于 X 的资料'），**代码完全一样，行为天差地别**：
> - **flash**：第 1 轮输出纯文本'让我先搜索一下知识库…'，但**没有发起真正的 function call**。我的 ReAct 循环靠'有没有工具调用请求'判断是否收尾——它没发工具调用，循环就误判'答完了'，第 1 轮就停了，吐了句 25 字的废答案。
> - **pro**：第 1 轮正确发起 `searchKnowledge` 工具调用，还**主动把查询词扩展**成'同程 旅游 酒店 机票 收益策略'等相关词；第 2 轮基于检索结果给出结构化答案后收敛。
>
> 这让我意识到：**agent 的'自主性'不只取决于框架，更取决于模型的 function-calling 遵循度——弱模型会从协议层面破坏 ReAct 循环**（'intent without action'，光说不练）。所以 agent 选型时，function calling 的稳定性比单纯的对话质量更关键。"

**这个案例的延伸（能继续聊的兜底设计）**
- 针对'光说不练'可以加防御：检测模型文本里有'让我搜索/查询'意图但实际没发工具调用 → 自动追加提示'请直接调用工具'再 re-prompt 一轮。这把'模型能力短板'用工程手段补上，正好呼应 [[故事 #6 的分层兜底]]。
- 更进一步：**主模型熔断 → 自动切备用模型**（多供应商冗余），是高可用 agent 的标配，目前我是单模型，这是会优先补的一环。

**我最终怎么修的（B+A 两层，已落地验证，最完整的一条）**
> "我要求 agent 对所有模型行为一致。深挖'光说不练'的根因，发现不在 prompt——而在**流式**：流式模式下工具调用要靠增量片段拼接还原，**这是跨模型最不一致的地方**（多步任务 + 模型先吐旁白时，tool_call 经常被顶掉）。我做了两层修复：
> - **B（机制级）**：ReAct 循环的模型调用从流式改**非流式**——返回完整的 `{content, tool_calls}` 对象，跨模型一致；过程事件（思考、工具调用）仍走 SSE 实时推给前端，只有最终答案改成整段投递。**关键是区分两层流式：SSE 传输流式（前端，不变）≠ 模型调用流式（改成非流式）。**
> - **A（兜底）**：加'未兑现工具意图'的启发式守卫——任何模型只要没发 tool_call 但文字像'我要调工具'，就注入纠偏提示重试，**不依赖任何厂商，是模型无关的安全网**。
>
> 上线后多步工具链（getCurrentTime→自定义业务工具）稳定执行，而且**兜底层基本不触发——B 这个机制级修复解决了主问题，A 备而不用**。我的原则：**机制差异用架构消除，能力差异用兜底吸收。**"

**追问预案**
- "非流式不是丢了流式体验？"→ 只有最终答案那段不再逐 token；思考/工具调用过程事件仍实时。这是用一点点最终答案的流式体验，换全模型的工具调用可靠性，权衡值得。要找回也容易：最终答案轮单独走一次流式生成。
- "A 的启发式会误判吗？"→ 会有边界（靠'调用/查询'等措辞 + 文本长度判断），所以设了重试上限 2 次防死循环，且 B 已让 A 极少触发。更稳可换成'本轮无 tool_call 且整轮无进展'的结构化信号。

## 故事 #7 · 真流式输出 SSE（你刚做的，有真实改造故事）

**会被问**
- 流式输出怎么实现的？
- 假流式和真流式的区别？

**你的素材（真实重构）**
- **我发现原来是"假流式"**：`AnalysisStreamService` 先同步阻塞跑完整个 `analyze()`，再一次性把所有事件 emit 出去——用户看着是流式，其实等了全程。
- 改造成真流式：新增 `analyzeStreaming()` 链路，一路透传到 `ReActLoopRunner.runStreaming()`，模型 token 通过 `StreamingChatLanguageModel` 逐个回调 `emitToken`，SSE 实时下发。
- 事件是结构化的（thinking step / token / tool call / done / error），不是裸 token 直通。

**讲出取舍（加分）**
> "真流式的价值不只是体验——它把**首 token 时间**从'等全程'降到'等第一步'，长任务体感天差地别。
>
> 但我没做成纯 token 直通，而是结构化事件：因为 agent 有思考、工具调用这些阶段，前端要分别渲染'正在思考''正在查数据库'，纯 token 流做不到这种分阶段展示。这是 agent 流式和普通 chatbot 流式的区别。"

**追问陷阱**
- "SSE 和 WebSocket 怎么选？"→ 单向下推 SSE 够了，更简单、自动重连；双向交互才上 WebSocket。

## 故事 #8 · 工具设计：原子积木 vs 成品流程

**会被问**
- 工具怎么设计的？粒度怎么定？
- 工具多了模型选不准怎么办？

**你的素材 + 反思**
- 17 个 `@Tool` 方法，`AgentToolInvoker` 自动生成规格。
- **我反思过粒度问题**：有些工具偏"成品流程"（如 `analyzeFileData` 把读取+解析+概览打包），这其实削弱了模型的组合能力——好的 agent 应该拿到 `readFile`、`runSql` 这种**原子积木**自己拼，工具越像成品，模型越退化成参数填充器。

**讲出取舍（加分）**
> "工具粒度是个真实权衡：原子工具（read/sql/calculate）给模型最大组合自由，最像智能，但要更多轮次、更贵；成品工具（一个工具搞定一类任务）省轮次、更可控，但模型自主空间小。
>
> Claude Code 那种故意只给原子工具（read/write/bash/grep），让模型自己编排重构流程。我现在理解了这个设计哲学——之前我的 Skill 系统就是反面：把流程写死，agent 只能选哪条流程，那不是自主。"

**追问陷阱**
- "工具太多模型选错怎么办？"→ 工具描述写清楚（模型靠 description 选）、按 agent 场景裁剪可见工具集（我的 `buildToolSpecifications(List<String>)` 就是按配置过滤）、必要时分层（先选工具组再选工具）。

## 故事 #9 · 安全与多租户（企业场景必问，也是你的料）

**会被问**
- agent 接了数据库/外部 API，怎么防滥用？
- 多租户数据怎么隔离？
- 防 prompt 注入吗？

**你的素材**
- 多租户：`SecurityContextHelper.getCurrentTenantId()`，所有查询带 `tenant_id`，共享数据用 `tenant_id=default`。
- RBAC：`sys_user/role/permission` 五张表，`*:*` 和 `app:use` 权限，管理员接口 ADMIN 保护。
- `OutboundUrlGuard`：拦截出站 URL（防 SSRF——工具能调外部 API 就有 SSRF 风险）。
- 敏感字段加密：`APP_ENCRYPTION_KEY`。
- JWT 无状态认证。

**讲出取舍（加分）**
> "agent 比普通系统危险，因为它**能自主调用工具触达真实资源**——能查库就可能越权查别人租户，能调 URL 就可能 SSRF 打内网。所以我的隔离不在应用层判断，而是每个查询强制带租户 ID，从数据访问层兜底。
>
> 出站 URL 我加了 `OutboundUrlGuard`，因为'让模型调外部 API'这个能力天然是 SSRF 入口，不能让它访问内网地址。这是 agent 特有的攻击面，普通 CRUD 系统不用考虑。"

**追问陷阱**
- "怎么防 prompt 注入？"→ **可能是洞**，提前想：用户上传的文件/知识库内容可能藏指令。防御：把检索内容明确标记为"数据非指令"、关键动作要审批、最小权限工具集。诚实说这块我还在加强。

## 故事 #11 · 用 LangGraph 风格的状态图重构 agent（手写过最小图引擎，硬素材）

> 这条是"总纲故事"提到的演进方向①的落地证据。能讲明白它，等于证明你不只会用框架，还懂 agent 编排框架的底层机制。

**会被问**
- LangGraph 是什么？跟你手写的 ReAct 循环有什么区别？
- 多 agent / 复杂流程怎么编排才可控？
- agent 要做危险操作（删库、转账、改价）怎么办？

**你的素材（手写过最小图引擎）**
- 我在项目里写了个独立的最小状态图引擎（`com.ai.graphdemo`，约 200 行），把埋在 `ReActLoopRunner` 的 while/if **显式化成"节点 + 边"**，吃透了 LangGraph 的核心：
  - **State**：贯穿全程的共享状态，每个节点读写它 —— 解决"各编排层不共享状态"。
  - **Node**：一步（LLM 推理 / 调工具 / 检索），吃 State 吐 State。
  - **条件边（conditional edge）**：节点执行完，由 State（通常是模型输出）决定下一个去哪 —— **这就是 LLM-as-router 的落点**。
  - **interrupt（中断点）**：把危险节点标为"执行前需人工审批"，运行到它前面会暂停并 checkpoint 当前位置，审批通过后 resume —— **这就是 human-in-the-loop**。
- demo 跑通了一条：`retrieve → agent →(条件边)→ 安全工具(成环) / 危险工具(⏸审批) / 收尾 → END`，危险动作 `updatePrice` 会卡在审批中断点，批准后才执行。

**讲出取舍 / 升华（加分）**
> "LangGraph 是 Python 的，我的栈是 Java/LangChain4j，所以我没直接用它，而是**自己实现了它的核心模式**——因为'图'本质就是 节点表 + 边表 + 一个按边跳转的运行循环，语言无关。手写一遍我才真正理解它相比裸 while 循环多出来的价值：**显式的流程可视化、每步 checkpoint 可暂停恢复、以及最关键的 interrupt 审批点**。
>
> 而 interrupt 恰好把我对企业 agent 的判断落了地——**'带刹车的自主'：模型通过条件边自主驱动推理，但在危险动作（改价/删库/转账）前用 interrupt 插人工审批。这就是'编排动作，不要编排推理'变成一张可执行的图**。"

**追问陷阱**
- "你这是不是重复造轮子？"→ 生产会用 langgraph4j（社区 Java 移植）；我手写是为了吃透机制、面试能讲到原理。造轮子是学习手段，不是生产方案。
- "和你主项目什么关系？"→ 独立 demo，不污染主项目的 ReAct 实现；主项目我做的是'自主模式默认 + 非流式工具调用'，是往模型优先挪的第一步，graph 是更彻底的形态。

## 故事 #12 · Prompt 工程：我实测过 prompt 到底控制什么（搞破坏式验证）

**会被问**
- system prompt 该写什么、不该写什么？
- 为什么有时候 prompt 里写了模型不听？

**你的素材（亲手做过三个对照实验）**
- **实验 A**：把 system prompt 里的工具说明全删光，只留一句角色 → 模型照样多步调用工具（getCurrentTime→自定义工具）。**证明：工具调用的机制由原生 function calling 的 schema 提供（每次传 N 份工具 schema），跟 prompt 文本无关**。很多人往 prompt 里塞工具说明，在原生 function calling 下基本是冗余。
- **实验 B**：角色加"必须用英文回答" → 模型仍用中文。**弱指令撞上"用户用中文提问"这个强先验，输了**。
- **实验 B'**：角色加"每条回复以🦜播报开头" → 真生效了。**同样一句 prompt 指令，不跟更强信号冲突就赢**。

**讲出结论（加分）**
> "这三个实验让我对 prompt 的理解从'写了就执行'升级成'**prompt 是参与博弈的带权重信号**'：① 它不控制工具机制（那是 schema），② 它能影响风格/行为，但**强度 + 是否与更强信号（用户语言、上下文、工具结果）冲突，决定它赢还是输**。所以写 system prompt：别浪费篇幅教模型怎么调工具；要让关键指令够强、够显眼、不跟上下文打架。"

**追问陷阱**
- "那怎么可靠强制英文输出？"→ 强化+重复指令、放在显眼位置、必要时在每轮注入、或后处理校验；单靠一句弱指令不可靠。
- "system prompt 和 few-shot 例子哪个更强？"→ 例子（演示）通常比抽象指令更强，因为模型更会模仿具体示范——这也是"信号强度"的体现。

## 附：可能被问到、提前准备的零散点

| 问题 | 一句话答案 |
|---|---|
| 结构化输出怎么保证？ | `callModelJson` 用 `response_format=json_object`，prompt 里必须含"JSON"字样 |
