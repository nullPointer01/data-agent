# 用户语义记忆

## 目标与边界

语义记忆用于跨会话保留当前用户明确表达或高置信度识别出的稳定信息，分为三类：

- `PREFERENCE`：沟通风格、输出格式等长期偏好。
- `ENTITY`：称呼、角色、公司、行业、专业领域等用户画像事实。
- `CONCLUSION`：用户已经确认、后续仍有复用价值的决定或结论。

短期 `SUMMARY` 保留为可管理的对话摘要，不参与结构化画像。v6 不再把全用户近期摘要自动注入当前回答；当前会话历史与工作状态、画像、相关长期检索分别装配，见 [Agent 运行时与 Harness](./Agent运行时与Harness.md#请求规划与资源准入)。管理员仍只能治理平台资源，不能读取其他用户的个人语义记忆；所有查询、修改和删除都同时约束 `tenantId + userId`。

## 写入链路

显式写入在回答前通过受治理工具完成；隐式候选与会话消息同事务持久化后执行：

```text
显式保存：AiServices -> GovernedToolSession -> saveMemory
  -> SemanticMemoryExtractor（本轮用户原文与显式保存准入，计入 Run 预算）
  -> SemanticMemoryService -> MySQL 记忆 + MEMORY 索引任务
  -> 工具返回保存数量与索引状态 -> 模型最终回答

隐式提取：AgentConversationRecorder -> SessionManager（同一 MySQL 事务）
  -> 保存用户/助手消息与会话统计
  -> ConversationMemoryCaptureService
       -> 同步保存 SHORT_TERM / SUMMARY
       -> 复用请求规划结果 memoryCapture，不增加分类模型调用
       -> SKIP：不调用长期记忆提取模型
       -> BACKGROUND：保存加密 memory_extraction_task，关联真实用户消息 ID
            -> 提交后通知 RabbitMQ -> MemoryExtractionWorker
            -> 同一个 SemanticMemoryExtractor.extract
            -> 一次 JSON 模型调用：内容 + 表达行为 + 适用范围
            -> 严格类型、证据、安全与跨会话准入校验
            -> SemanticMemoryService 核验租约、来源、用户修订与消息水位后写入
                 -> LongTermMemory：MySQL 记忆与 MEMORY 索引任务同事务提交
                 -> IndexTaskWorker：后台 Embedding -> Milvus，失败按任务重试
       -> UserProfileMemoryRefreshService 完整重建画像
```

v9 的 `memoryCapture` 由现有语义 Router 与意图、上下文需求一起输出，只保留 SKIP/BACKGROUND。普通问答、回忆提问、假设/引用和临时格式要求为 SKIP；新陈述的稳定个人事实可为 BACKGROUND。明确保存/纠正应选择已绑定的 saveMemory，明确忘记应选择 forgetMemory，后台提取不接受显式候选。没有绑定工具不能通过自动提取绕过授权。规划不可用或合同非法时保守 SKIP，廉价短期摘要照常保存。

saveMemory 返回实际保存数量、success 和索引待处理状态；空候选不报告成功。工具选中时首轮使用 REQUIRED，要求实际工具调用，但这不保证模型一定选对后续步骤。forgetMemory 通过类型化模型核验本轮真实删除意图、目标和逐字证据，再在短事务内重验本人归属与目标正文未变。模型语义判断仍可能出错，目标歧义应先澄清。两条提取路径复用原结构化模型入口、配额与用量记账，`semantic-extraction-enabled=false` 会停止保存提取；忘记已有记忆仍可执行。记忆中心区分主库已保存、索引处理中/重试/失败/完成，模型文字不是写入凭证。

## 异步索引与召回核验

长期记忆新增、覆盖、晋升、用户删除、配额裁剪和到期清理，都与 MEMORY 任务在同一 MySQL 事务中提交。外部 Embedding/Milvus 调用由 Spring AMQP 监听消费者执行，继续使用来源去重、版本、租约和有限重试。本轮增加 RabbitMQ，以及提取任务和用户修订状态两张表，由 Flyway V3 升级。

`LongTermMemory.recall` 先按租户、用户与 MEMORY 类型检索，再批量核验主库中的身份、LONG_TERM 层级和有效期。已删除/失效记录不进入上下文；索引片段必须仍存在于当前有效正文中，已被修改的旧片段会被丢弃。只返回经过核验的命中片段，不用旧向量得分替新正文背书。该策略优先避免引用失效证据，后台索引延迟期间可能少召回。

完整问答的 CONVERSATION 索引写入、消费者分支和载荷代码已删除，V3 取消历史任务并移除旧 payload 列。历史 Milvus 向量不自动删除，也不参与当前召回。当前会话历史仍从 MySQL 读取。

原两秒索引扫描、独立索引执行池和内存语义提取任务已移除。正常由事务提交后发送任务 ID，消费者 CAS 认领，落库后 ACK；每分钟只补偿漏投、到期重试与失效租约，活跃任务每十秒续租。五次执行失败后保留 FAILED 并拒绝到死信队列；每次领取即累计尝试，连续进程崩溃也受次数限制。实际重试时刻还受一分钟补偿周期影响。主库任务是恢复依据，发布确认不代表业务成功，也不宣称模型调用不重复计费。

请求开始前快照 `memory_write_state.revision`；用户保存、修正、删除和清空推进修订。后台提交锁住用户状态，拒绝旧修订、迟到旧消息与失效来源，避免删除后旧任务重新写回。该保护比较保守：一次显式操作也会使此前尚未提交的其他隐式候选失效。完整架构、配置、断点和验收输入见 [记忆与后台任务技术方案](./记忆与后台任务技术方案.md)。

## 提取准入

`SemanticMemoryExtractor` 对模型输出执行以下硬校验：

1. 一轮最多接收 3 条候选。
2. 类型只允许 `PREFERENCE / ENTITY / CONCLUSION`。
3. `semanticKey` 必须位于 `preference.* / profile.* / conclusion.*` 命名空间。
4. `evidence` 必须逐字存在于用户原话，助手回复不能作为事实证据。
5. 隐式候选置信度默认不得低于 `0.85`。
6. 密码、API Key、Token、身份证和银行卡等敏感信息不得写入。
7. speechAct 仅接受用户事实/偏好陈述 ASSERTION 或当前真实保存请求 SAVE_REQUEST；提问、引用、假设和拒绝保存不准入。
8. scope 必须是 CROSS_SESSION；本次任务/步骤/格式/检索约束属于 CURRENT_TASK。混合句逐候选判断，保留稳定事实而不连带保存临时要求。
9. 类型与键前缀必须匹配，置信度为有限的 [0,1] 数字；拒绝缺字段、null、未知字段、重复字段、数字枚举、字符串强转及多余 JSON。超长内容拒绝，不截断成看似有效的事实。

已删除“包含记住/偏好/默认就存储”的词表、逐项正则提取、通用整句哈希兜底和拼接截取 JSON 的容错路径。偏好修正仍使用稳定属性键，例如明确“以后改用列表”覆盖输出格式；本次“用列表”不覆盖。scope/speechAct 是模型语义判断，服务端只准入合法判断和证据，不代表语义误判已不可能发生。

## 稳定键与覆盖

`memory_entry.semantic_key` 表示可覆盖属性，`confidence` 表示本条语义记忆的提取置信度。数据库唯一键为：

```text
(tenant_id, user_id, type, semantic_key)
```

同一用户再次表达同一属性时更新原记录并提交向量重建任务，不新增重复记录。批内重复候选也会先按 `type + semanticKey` 合并。新建记录前执行用户记忆配额裁剪，覆盖已有记录不会误删其他记忆。

当前参与结构化画像的固定键包括：

- `profile.display_name`
- `profile.role`
- `profile.company`
- `profile.industry`
- `preference.communication_style`
- `preference.output_format`
- `profile.expertise_area.*`
- `profile.topic.*`
- `profile.data_source.*`

无法映射到具体画像字段的通用语义记忆仍可在分类卡片中查看和修正，但不会抬高结构化画像置信度。

## 画像重建

`user_profile` 是语义记忆的可重建投影，不是独立事实源。画像只读取长期 `PREFERENCE / ENTITY`，按更新时间倒序取最新值；摘要、结论和没有合法稳定键的旧记录均不参与投影。

每次新增、覆盖、修正、删除或清理语义记忆后，系统根据当前有效证据完整替换画像。没有实际投影成功的证据时删除旧画像，避免已经删除或修正的信息被历史快照永久合并回来。

## 用户纠错

### 重置用户画像

记忆中心的“结构化画像”提供“重置画像”按钮，确认后调用 `POST /api/v1/memories/profile/reset`。画像是长期记忆的结构化投影，不等于全部长期记忆。

重置只删除当前租户、当前用户的上述固定画像键及三个列表前缀对应的长期 `PREFERENCE / ENTITY` 依据，并重建为空画像。其他通用偏好、通用事实、长期结论、短期摘要、聊天记录、账号与 Agent 设置保留。删除全部对应依据，不受页面显示条数或画像取证 200 条上限限制；没有画像时重复重置也成功，不新增表或配置。

同一 MySQL 事务内推进用户记忆修订号、分批删除依据、登记 MEMORY 向量清理任务、清空画像并写审计。重置前未提交的隐式提取因旧修订失效；画像重建在用户写锁内读取最新依据，避免并发旧快照写回。长期衰减只条件更新现有记录，不能通过保存陈旧实体重新插入已删除依据。Milvus 清理由既有后台任务执行，完成前召回仍经主库核验，已删依据不进入新上下文。

重置不是“清空历史”：已开始执行的模型请求可能已装配旧上下文，当前会话历史中也可能仍含原信息。若要验证跨会话遗忘，应新建对话；后续重新明确表达并保存的稳定信息可重新建立画像。

人工验收：记录画像与非画像结论各一条 → 点击重置并确认 → 画像字段和置信度归空、对应依据消失、结论和聊天记录保留 → 刷新/重登仍为空 → 另一账号不受影响 → 再记录新画像信息可正常重建。另需验证旧后台提取到达时不写回，以及超过 200 条画像依据能完整删除。本轮仅完成源码和静态检查，未执行这些运行验收。

记忆中心的偏好、画像事实和结论卡片展示来源、置信度和更新时间，并提供修正与删除操作。修正接口为：

```http
PUT /api/v1/memories/{memoryId}
Content-Type: application/json

{"content":"新的记忆内容"}
```

接口只允许当前用户修改自己的长期语义记忆，最多 500 个字符。修改后置信度置为 `1.0`、来源置为 `USER_EXPLICIT`，提交向量重建任务并刷新画像。短期摘要只能删除，不能伪装成用户确认的语义事实。

## 数据库升级

新库由 `sql/init.sql` 创建字段和唯一键；已有数据库执行：

```bash
mysql -h127.0.0.1 -uroot -p data_agent < sql/upgrade-semantic-memory.sql
```

升级脚本幂等检查字段和索引。旧的错误 `user_profile` 可以精确删除，原始记忆无需清理；后续有效语义记忆会重新生成画像。

## 验收用例

1. 输入“请记住：以后回答保持简洁，优先使用表格”。
2. 记忆中心应出现两条 `PREFERENCE`，结构化画像显示“简洁直接 / 表格优先”。
3. 输入“请记住：以后不要使用表格，改用列表，并且需要详细说明”。
4. 原两条稳定键记录应被覆盖，记忆总数不因同属性重复增加；画像变为“详细解释 / 列表优先”。
5. 在卡片中修正任一语义记忆，刷新后内容、来源、置信度、更新时间和画像投影应同步更新。
6. 删除画像证据后，对应画像字段应消失；删除最后一条有效画像证据后 `user_profile` 不再保留空快照。
