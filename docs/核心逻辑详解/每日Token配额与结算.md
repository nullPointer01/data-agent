# 每日 Token 配额与结算

更新时间：2026-10-10。本批完成源码改造与静态检查；未编译、启动、执行数据库迁移或真实调用验收。

## 解决什么问题

原逻辑先汇总当天明细，再决定是否放行。两个并发请求都可能读到同一余额并同时调用模型；失败、重试和取消也可能漏记。现在以 MySQL 日账本作为准入依据，每次实际调用先原子预占，再在网络请求完成后结算。统计明细和余额在同一事务更新，不再靠事后 SUM 控制并发。

每日配额与单个 Agent Run 预算是两层限制：每日配额跨请求、跨实例持久化；Run 的超时、迭代、模型次数、工具次数与 Token 限制继续负责单次任务。子 Agent 使用同一用户日账本，继续共享根 Run 预算。

## 一次调用怎么走

1. `McpModelService` 治理上下文，解析最终模型客户端和身份。`TokenQuotaGuard` 估算输入、工具与响应 Schema 的 Token，添加安全余量，取得请求或模型配置的输出上限。
2. `TokenQuotaService.reserve` 在独立短事务锁定 `(tenant_id, user_id, quota_date)` 日账本。可用额度等于上限减已记账和进行中预占；不够容纳输入与最低输出时拒绝，否则必要时缩小输出上限并创建独立调用 ID。
3. 通过 LangChain4j 官方 `ChatRequest.toBuilder().maxOutputTokens(...)` 设置上限，保留工具、格式与厂商参数。发送前将预占标为 DISPATCHED，随后在事务外调用厂商。网络等待不持有数据库行锁。
4. 完整响应优先采用厂商 TokenUsage，缺字段时按完整响应估算；先结算用量，再校验回答内容。空回答或业务校验失败不代表厂商没消耗 Token。
5. 同一短事务更新日账本、预占终态和唯一调用明细。重复回调不重复扣额；每次同步重试使用新的调用 ID，流式仍不自动重试。回调恢复发起方租户、用户与 Run 上下文。

临时模型连接探测也执行预占/结算，但不进入 Agent Run、不缓存客户端、不保存提示词和回复，明细模型名称显示“连接探测”。它仍最多请求 32 输出 Token，且不自动重试。

## 状态与失败语义

| 预占状态 | 含义 | 对余额的影响 |
| --- | --- | --- |
| PENDING | 已预占，尚未标记发送 | 占用 reserved |
| DISPATCHED | 已确认发送准入，可能已到达厂商 | 继续占用 reserved |
| SETTLED | 收到完整响应并完成用量结算 | 释放预占，按 ACTUAL 或 ESTIMATED 计入 charged |
| RELEASED | 发送标记前失败或过期 | 释放预占，不记模型用量 |
| UNKNOWN | 标记发送后失败、取消、超时或进程失联，缺少完整用量 | 将整个预占额计入 charged 和 uncertain |

DISPATCHED 是本地发送边界，不能证明厂商收到或计费。即使厂商返回认证错误等 HTTP 错误，当前也按 UNKNOWN 保守预扣；它不是收费事实。UNKNOWN 明细的输入/输出为 0 占位，页面显示“-”，不能用于计算真实输入/输出。

流式取消后，只要 SDK 仍回调完整响应，就允许 UNKNOWN 校正为完整用量并退还多扣的日余额。校正不会重新输出回答、执行工具或恢复已终止 Run。根 Run 使用每次尝试独立的记账水位防止重复计数；UNKNOWN 后退款不降低已计入 Run 的保守值。

结算数据库失败会向上抛出记账异常，不静默吞掉、不因此重试模型。未确认的预占留在账本，防止“模型已经消耗，但额度被释放”。

进程崩溃恢复不增加定时扫库：本人下次调用或查询余额时，按日期升序限量处理最多 25 个过期预占，包括历史日期。PENDING 释放，DISPATCHED 转 UNKNOWN，结算回原配额日。历史积压超过 25 个需要后续调用/查询继续处理；无人访问的遗留单不会主动恢复。

## 存储与配置

新增 Flyway `V7__daily_token_reservations.sql`，未执行：

- `token_daily_quota`：租户、用户、配额日联合主键，保存 charged/reserved/uncertain 三个计数。
- `token_reservation`：每次实际尝试的 UUID、输入估算、输出限制、预占额、状态与有效期；按本人身份和有效期查询。
- `token_usage`：增加 invocation_id 唯一键、quota_date、accounting_status；model_id 扩为 255，与模型配置主键一致。

V7 保留历史明细，以旧 created_at 的日期初始化日账本，历史状态标记 LEGACY，不能宣称其全部是厂商真实用量。不修改 V1～V6。启动启用 Flyway 后才会执行本迁移；不能只更新后端而跳过数据库升级，也不能混跑仍只写旧明细的旧后端。

公共配置在 `application.yml` 的 `app.token-quota`，local/prod 继承：

```yaml
daily-limit-per-user: 1000000
zone-id: Asia/Shanghai
reservation-ttl: PT10M
input-safety-tokens: 256
default-output-tokens: 4096
```

用户配额 0 继承全局值，-1 不限额，正整数采用个人上限。有效期至少 10 分钟，避免正常最长模型等待被误恢复；输出上限优先请求参数，其次模型默认值，最后 4096。跨午夜的调用始终结算到预占日，全部实例须使用同一时区；上线后改时区不会自动换算历史日账本。

## 页面与接口

`GET /api/v1/token/remaining-quota` 保留 success/remainingTokens，新增 quotaDate、zoneId、dailyLimit、chargedTokens、reservedTokens、uncertainTokens。剩余值已扣除进行中预占；不限额返回 -1。

统计页分开展示厂商用量 ACTUAL、完整响应估算 ESTIMATED、待核账预扣 UNKNOWN 和历史记录 LEGACY，新增本人今日余额、进行中预占与待核账额。累计记账包括估算与保守预扣，不能当成账单金额。输入/输出页内汇总排除 UNKNOWN。刷新汇总先完成本人过期恢复，再读取累计数；独立 HTTP 请求之间不承诺全局一致快照。

Token 明细只保留配额服务内的幂等写入口和实际使用的查询，删除无人调用的通用 CRUD。用户累计汇总显式包含租户与用户条件，租户统计/明细仍遵守管理端权限。

## 人工验收

使用专门的验收账号，先记录初始用量和配额，避免影响主账号。以下尚未执行，不能当成运行通过证据。

1. 迁移：重启后确认 Flyway V7 成功，两个新表和明细字段存在，历史记录为 LEGACY。重启第二次不重复灌入历史账本。
2. 正常完整响应：发送“用一句话解释 SSE”，观察预占释放、明细只增加一条、charged 按完整用量增加。查看最终请求的 maxOutputTokens 确实受预占限制。
3. 并发：将账号额度调到只够一次上下文与输出，两标签页同时请求较长回答；应出现输出收窄或拒绝，不能都按旧余额放行。每次尝试有不同 invocation_id，reserved 不为负。
4. 失败与取消：发起长回答后停止；若完整用量不可得，状态 UNKNOWN 且预占转为待核账扣额。若 SDK 回调迟到完整响应，应只校正账本，页面不能恢复输出。真实厂商费用与本地预扣分别观察。
5. 重试与记账故障：在受控环境触发可重试网络故障，核对每次实际尝试各自记账；数据库故障时不能绕过预占调用模型，也不能因结算失败再调模型。恢复数据库后检查遗留预占。
6. 崩溃：预占 PENDING 和 DISPATCHED 两种阶段分别停止进程，超过有效期后重启，用原账号查余额，确认分别释放和 UNKNOWN；另一账号不触发这些预占的恢复。
7. 边界：验证不同租户/用户不共享余额，-1 不限额、0 继承配置、非法负数被拒绝；跨午夜仍记原日。连接探测应受日额度约束且不保存对话正文。

## 明确限制

输入估算与 256 Token 安全余量无法保证覆盖所有厂商隐藏开销，输出上限也依赖厂商遵守协议。实际用量超过预占时仍按真实响应记账，可以使当天超额，随后阻止新的调用；这是并发准入治理，不是厂商账单的数学硬上限。

本账本覆盖聊天模型请求及临时连接探测，不覆盖 Embedding、精排等独立服务的计费。

当前没有厂商账单对账 API 或管理员人工核销接口，UNKNOWN 只支持迟到完整响应自动校正，可能长期保守多扣。预占记录尚未增加独立保留清理策略；不得任意删除未结算单或直接修改明细，否则会破坏日账本一致性。

后续批次继续长任务摘要、审批事件与持久 Run 订阅等改造，本批不改变那些运行机制。
