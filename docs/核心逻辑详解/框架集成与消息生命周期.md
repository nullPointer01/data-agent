# 框架集成与消息生命周期

标准 MCP 外部工具已接入同一 AiServices 治理链：官方客户端负责协议，项目负责配置、绑定和授权。它位于 `com.ai.integration.mcp`，与下文历史模型网关 `com.ai.mcp` 不同；配置、断点和 Schema 限制见 [标准 MCP 工具接入](./标准MCP工具接入.md)。

## 目标与边界

2026-09-29 将 LangChain4j Core/OpenAI 升级至 Maven Central 当日最新正式版 1.20.2，Milvus 使用对应 1.20.2-beta30；2026-09-30 接入同版本系列的官方 Reactor 适配模块 1.20.2-beta30（该模块仍为 beta）。通用模型协议、助手代理、消息窗口、流式事件、工具参数绑定和融合排序优先用框架。业务身份、预算、审批和持久化事务仍由 Harness 管理。

| 能力 | 框架负责 | 项目负责 |

| 流式回答 | 官方 Flux 适配、StreamingChatModel 与 SDK 增量回调；MVC 编码 SSE | SSE 业务事件、有界缓冲、取消、Run 终态、Token 记账 |
| 对话窗口 | MessageWindowChatMemory；Skill 使用 TokenWindowChatMemory | 从已鉴权会话装配历史，成功轮次的数据库事务 |
| 结构化任务 | AiServices 类型返回、由 Java 类型生成原生 Schema、OutputGuardrail | Router 工具授权、记忆原文证据及持久范围准入 |
| 语义记忆 | EmbeddingModel、EmbeddingStore/MilvusEmbeddingStore | 用户纠错、租户过滤与长期记忆存储 |
| 文档解析 | 官方 PDFBox / POI DocumentParser、TextDocumentParser | 类型白名单、Excel 表格输出、文件业务状态与归属 |
| RAG | 官方中文句界与递归 DocumentSplitter、查询 Transformers、EmbeddingStoreContentRetriever、DefaultRetrievalAugmentor、ReciprocalRankFuser、DefaultContentInjector | 身份与调用治理适配、BM25、章节/来源位置、精排降级、父上下文、引用和评测 |

| Function Calling | AiServices 工具循环、@Tool/@P、ToolSpecifications、DefaultToolExecutor、原生消息协议 | 整批准入、授权、风险、审批、幂等、恢复与根 Run 预算 |

## 从一次聊天读代码

文档解析与查询检索的框架入口、配置和断点见 [文档解析与框架检索](./文档解析与框架检索.md)。查询变换不再使用业务词表；当前没有把另一个无条件 Retriever 挂到 AiServices，避免与知识预加载/工具入口重复召回。

```text
SessionManager 读取当前用户的 MySQL/Redis 会话
  → Coordinator 创建并注册 PLANNING Run，发出开始事件
  → Router 在同一 Run 内规划，绑定最终模式并保留控制器与预算
  → ConfiguredAgentExecutionService 按计划准备角色化历史及个人记忆
  → ConfigurableAgentExecutor 装配 SystemMessage / 历史 / 当前 UserMessage
  → AgentChatService 拆出指令与当前问题，历史预填本次独立 ChatMemory
  → AiServices 从 @SystemMessage / @V 生成唯一的系统消息并置顶
  → McpModelService 的受治理 ChatModel / StreamingChatModel 适配器
  → ModelClientRegistry 选择当前租户的厂商客户端
  → 框架返回 Result 或 Flux<AiServiceStreamingEvent>
  → Runtime 统一保存会话、更新 Run 与 Trace
```

建议先读 [AgentChatAssistant](../../src/main/java/com/ai/agent/AgentChatAssistant.java)，接口描述“调用后要得到什么”；再读 [AgentChatService](../../src/main/java/com/ai/agent/AgentChatService.java)，看 AiServices 如何创建代理；最后读 [McpModelService](../../src/main/java/com/ai/mcp/McpModelService.java)，看真实模型调用前后的准入与记账。

会话把当前已加载历史（数据库最多 50 条）保留为 user/assistant 角色，不再固定截取六条，也不逐条截断到 500 字。规划器仍可读取紧凑预览；回答模型的 Token 准入由 AgentContextGovernor 负责。TokenMonitor 统一实现框架 TokenCountEstimator；显式配置的模型词表使用 OpenAiTokenCountEstimator，未映射模型按 UTF-8 字节保守预留。AgentContextGovernor 按预算保留完整用户轮次及工具组；系统规则、当前输入放不下时明确拒绝。local/prod 均开启无模型摘要的完整轮次裁剪。框架窗口只管理本次消息，不额外覆盖产品历史；Skill 当前输入先经过准入，再写入窗口，避免被提前淘汰。

## 为什么没有把聊天表直接改成 ChatMemoryStore

ChatMemoryStore 提供 getMessages/updateMessages/deleteMessages 扩展接口。窗口新增消息和淘汰消息时都会更新它；它管理的是模型当前能看到的消息，不是产品聊天记录。

本项目 [SessionManager](../../src/main/java/com/ai/service/SessionManager.java) 还承担用户/租户鉴权、完整历史、按 Run 幂等保存、标题和审批消息更新。直接用框架窗口覆盖这张表，会把淘汰误当删除，并可能在模型失败前就写入未完成轮次。

因此本次使用框架默认的内存窗口存储，按请求从已经鉴权的持久记录重建；数据库仍只有原有事实来源。退出再登录、重启应用后的会话恢复依赖现有 MySQL 记录，不依赖这个临时窗口。长期偏好及工作记忆也不是 ChatMemoryStore 的等价物，其业务存储保留。

如果将来需要把“包含工具过程的模型窗口”跨请求独立持久化，再实现单独的 ChatMemoryStore 适配器，并明确事务、租户身份及淘汰策略；当前不能为了实现一个接口而增加第二份状态。

## 注解提示词：从这个接口开始学习

```java
@SystemMessage("{{systemPrompt}}")
Flux<AiServiceStreamingEvent> stream(
        @V("systemPrompt") String systemPrompt,
        @UserMessage String message);
```

`@SystemMessage` 定义系统消息模板，`@V` 将本次已经装配好的 Agent 指令填入模板，`@UserMessage` 标明当前用户输入。系统指令仍按 Agent 配置与权限动态生成，注解不意味着所有用户共用固定人设。`AiServices.builder(AgentChatAssistant.class)` 创建接口代理；用户调用代理方法时，框架组装消息并调用模型。

AgentChatService 只向窗口预填历史。框架默认把后来加入的系统消息放在末尾，因此显式配置 `alwaysKeepSystemMessageFirst(true)`，让注解生成的系统消息位于首位，不重复手工添加指令。每个 Run 新建窗口，避免用户之间串历史或人设。

默认角色统一为通用个人 Agent。AgentSystemPrompts 管理中性的公共行为规则和默认角色，AgentProfileService 创建新默认 Agent 时引用同一常量。空角色使用通用兜底；旧工厂原样写入的个人角色在组装时精确归一化，解除旧“每个副作用都要聊天确认”与服务端审批规则的冲突。其他自定义角色原样保留，包括用户主动配置的数据分析专家；不执行数据库批量覆盖。

公共规则不再无条件要求 calculate，也不强制所有任务“一次只推进一步”。可用工具由本次工具声明决定，有依赖动作等待前序结果，是否并行由服务端决定；本次改动没有启用并行工具执行。提示词是模型行为建议，实际权限与审批仍由代码强制校验。

## Agentic：把专家委派的步骤交给框架

`langchain4j-agentic` 是 AiServices 之上的编排模块，提供顺序、条件、并行、循环以及 Supervisor 等组合方式。当前接入与 Core 1.20.2 配套的 1.20.2-beta30；官方将该模块标为实验性。项目已经使用专家顺序工作流和可切换 Supervisor，不能把模块提供的全部能力写成项目已经实现。下面先介绍两条路径共用的专家内部工作流；外层动态管理者见 [Supervisor 与原编排对照](./Supervisor与原编排对照.md)。

实际入口为 [AgentDelegationToolService](../../src/main/java/com/ai/agent/tool/AgentDelegationToolService.java)，工作流在 [AgenticDelegationWorkflow](../../src/main/java/com/ai/agent/agentic/AgenticDelegationWorkflow.java)：

```text
父 Agent 通过 Tool Calling 选择绑定专家
  → delegateToAgent：检查绑定、租户、启用、任务长度、防环路/深度
  → Agentic 顺序工作流
      PlanningStep：调用现有语义规划器，返回 plan
      ExecutionStep：接收 plan，调用专家的配置化执行器，返回 response
  → 专家结果作为原生工具结果返回父 Agent，由父 Agent 继续回答
```

核心声明只有：

```java
workflow = AgenticServices.sequenceBuilder(Delegation.class)
        .subAgents(new PlanningStep(planner), new ExecutionStep(executor))
        .outputKey("response")
        .build();
```

| 新概念 | 在这段实现中的作用 |
|---|---|
| `@Agent` | 把一个方法声明为编排节点；也支持普通 Java 节点，不表示每个注解都自动请求模型 |
| `sequenceBuilder` | 定义先规划再执行；第一步失败，后一步不执行 |
| `outputKey = "plan"` | 把规划节点返回值写入本次工作流状态 |
| `@V("plan")` | 自动读取上一步的 plan，作为执行节点参数 |
| `AgenticScope` | 本次工作流的参数、步骤结果与执行状态；不等同于 ChatMemory 或数据库聊天历史 |

这两个节点是已有受治理服务的 Java 适配节点：内部的规划和专家回答仍可能调用模型，模型调用继续使用原有 AiServices/Schema/预算链路。没有新建无治理模型客户端，没有为编排额外增加 Supervisor 推理请求。

框架代理在 Spring 中复用，但不指定 MemoryId，每次调用创建独立临时 AgenticScope；同步顺序节点不另起线程，保持当前 Run 与身份作用域，结束后框架清理状态。每步检查根 Run，规划和专家实际模型调用共享原预算。框架会包装节点异常，工作流边界只解开框架/反射包装，保留预算耗尽、取消和业务拒绝类型；不自动重试节点，也不把错误转为成功文本。

防环路/深度 Guard 包住整个工作流，因此非法委派会在规划调用前拒绝。持久化审批继续由现有 Harness 管理，本次没有将审批迁到 AgenticScopeStore，也没有声称支持任意嵌套审批恢复。

顺序工作流的价值是学习并实际使用框架的步骤编排、状态绑定和失败短路，不承诺两步改成框架后吞吐或回答质量自动提升。现已新增外层 Supervisor 对照路径，额外管理者调用和最终汇总的成本要通过真实任务比较，整图审批恢复暂不支持。

建议断点顺序：`delegateToAgent` → `AgenticDelegationWorkflow.execute` → `PlanningStep.plan` → `ExecutionStep.execute`。在最后一步查看 plan：它是框架从 AgenticScope 注入的同一个规划结果。无专家绑定的普通聊天不会进入此工作流，这是预期行为。

## 流式、异步和失败

模型侧与 HTTP 侧是两个不同职责的 Flux：

```text
厂商 SDK 增量回调
  → McpModelService 转为原生 ChatModelStreamingEvent 发布者
  → AiServices 官方适配器：Flux<AiServiceStreamingEvent>
  → PartialResponseEvent 即时发送；FinalResponseEvent 提供最终回答
  → Agent 业务事件（token / tool_call / approval_required / done）
  → AnalysisStreamService：Flux<ServerSentEvent<String>>
  → Spring MVC 订阅、编码 SSE → 浏览器 fetch 逐段解析
```

使用事件 Flux 是为了区分“工具轮中的文字”和“最后一轮的回答”。AgentChatService 的 `doOnNext` 实时转发片段，`FinalResponseEvent` 经 `toFuture()` 衔接 Coordinator 的保存与终态事务。Future 只表示整个回答何时完成，不会把中途片段攒到最后才发送。

Controller 直接声明 `Flux<ServerSentEvent<String>>` 和 `text/event-stream;charset=UTF-8`。AnalysisStreamService 的 `Flux.defer` 在订阅后才启动 Run，每个订阅独立管理状态；256 个事件的有界缓冲溢出、订阅取消或绝对超时会取消 Run。完成/等待审批先标记终态，客户端消费最后一帧后断开不会反向取消审批。前端 URL、JSON 事件结构和 fetch 解析方式保持兼容。

MvcStreamingConfig 为网络写入配置独立有界线程池、UTF-8 字符串编码和稍晚于业务时限的 Servlet 超时。项目仍为 Spring MVC：Spring 内部用 Servlet 异步支持处理 Flux，不必为了返回 Flux 切换整个应用到 WebFlux。网络断开通常在下一次写入时发现，不承诺瞬时检测。

厂商 SDK 在回调线程送出增量，CHAT 和正常工具对话都使用 CompletableFuture 将完成阶段传递至 Coordinator 和 AnalysisStreamService；模型等待期间释放 SSE 工作线程。ModelResponseStream 通过共享定时器每 250 毫秒检查 Run，流自身上限为 300 秒，较短的 Run 预算会提前结束。

TaskContextSnapshot 捕获身份、MDC、Run 和能力边界，回调执行后还原线程原状态；空快照也显式清空作用域。记账与完成动作交给独立的有界 modelCompletionExecutor，避免 ReAct 占用 SSE 池等待模型时，完成回调又排进同一个池。池满时由回调线程执行终态清理，避免丢失完成事件。应用停止主动结束未完成流。

Coordinator 从规划阶段就注册 Run；顶层与子 Agent 的规划均计入共享模型调用和 Token 预算。同步模型调用交给独立有界 modelInvocationExecutor，等待方每 250 毫秒检查取消与截止时间。规划完成通过 CAS 绑定最终模式，保留同一 Run ID 和控制器。规划失败也能记录 Trace。

Coordinator 只在回答成功保存后将 Run 置为完成，再发布结束事件并移除活跃 Run；保存失败传播为失败终态。取消返回 Future 不会跳过实际执行的终态清理；等待审批仍单独保存待审批会话。请求规划、数据库访问、RAG 和可恢复工具循环仍有同步阶段，因此不能称为整个系统端到端非阻塞。

失败传播异常，不能把错误提示当作成功回答入库。已经输出一部分后连接失败，不再同步重发整次请求。优先记录厂商最终 TokenUsage；失败且只有部分文本时按收到文本估算。尚未收到可用 StreamingHandle 时，只能先停止业务等待，底层连接可能等到 SDK 超时才释放。

模型、Embedding 和 Reranker 统一通过 ExternalCallPolicy 使用 Resilience4j。同步请求仅重试明确瞬时故障，模型每次实际尝试都扣调用预算；流式请求只接熔断，不自动重发。重试包在熔断器内部，一次逻辑调用只记一次成败。计数窗口最近 N 次全部失败后打开，等待配置时长后只允许一个半开探测。取消、中断和本地预算终止不计入厂商故障。

## 会话保存与持久索引任务

SessionManager 在一个事务内保存用户/助手消息、会话统计以及 index_task。会话行锁串行化同一会话的保存，按 Run 检查幂等；Redis 在提交后失效，回滚不留下伪成功缓存。审批恢复的最终回答也先保存并提交索引任务，再报告完成。非最终审批进度消息仍是尽力更新，权威状态保存在 durable Run。

知识新增、修改、删除和同步同样与索引任务一起提交。KnowledgeService 使用短 TransactionTemplate，异常先回滚再返回错误；批量上传每个文件独立提交。旧的进程内 KnowledgeVectorEvent 链已经删除。

文件上传创建元数据和删除元数据同样提交 FILE 任务，原进程内异步提交/即时向量清理已删除。IndexTaskProcessor 使用任务身份读取最新来源，知识与文件复用 RagDocumentIndexer 一次分块双索引；MEMORY 维护重建复用同一队列，仅索引有效长期记忆。管理接口、维护窗口和 ICU 契约见[中文检索与索引维护](./中文检索与索引维护.md)。

IndexTaskStore 合并同一来源的版本；IndexTaskWorker 扫描认领后进入有界线程池，按任务保存的租户和用户查主数据。60 秒租约每 10 秒续期，过期可被其他实例接管；索引异常最多执行 5 次，指数退避，之后保留失败状态供人工重试。旧执行完成不能覆盖新的数据库任务版本，失租晚到结果会再次安排最新版本补偿。对话载荷加密，按 Run 身份重放；成功的对话任务保留 30 天后分批清理。

知识页展示索引状态、自动刷新未完成任务；失败可重试，旧知识没有任务记录时显示待验证并允许建立索引。查询接口也保留已删除知识的清理任务。状态定义见[运行与索引状态](../术语/枚举速查/运行与索引状态.md)。

边界：MySQL、Milvus、ES 之间没有分布式事务。索引替换仍存在删除到重写的短暂窗口；外部已执行操作不能被数据库租约撤销，不宣称外部强 fencing 或 exactly-once。更新/删除期间可能短暂读到旧结果，恢复和重试用于补偿；真实双写恢复与极端失租崩溃场景仍需联调。任务版本也不等于 Embedding Profile 的模型/维度版本。

## 类型化路由与记忆提取

ModelSemanticRequestRouter 的 PlanningAssistant 返回 Decision；SemanticMemoryExtractor 的 MemoryAssistant 返回 Extraction。StructuredAssistantFactory 创建 AiServices，框架从返回类型生成 Schema；字段用 JsonProperty(required = true) 声明必填，原生客户端开启 strictJsonSchema。Router 保留显式 JSON_OBJECT 兼容模式，不自动切格式重发。

统一 OutputGuardrail 严格拒绝重复键、缺失/空字段、未知字段、错误类型、尾随 JSON、Markdown 包裹及超长输出，自动修补重试次数为 0。路由置信度、候选工具白名单和记忆的用户原文证据、表达行为、跨会话范围继续由业务校验。框架生成结构不等于模型可以决定权限。

## AiServices 工具循环与审批边界

[AgentToolRegistry](../../src/main/java/com/ai/agent/tool/governance/AgentToolRegistry.java) 已用框架从 @Tool/@P 生成参数 Schema，并用 DefaultToolExecutor 将模型 JSON 参数绑定到 Java 方法。模型选择工具的响应通过 ChatResponse.aiMessage().toolExecutionRequests() 读取，不是服务器从用户句子中匹配参数。

正常对话的工具循环已交给 AiServices。入口为 `AgentChatToolService -> AgentChatService`，注册的是 `Map<ToolSpecification, ToolExecutor>`，每个执行器调用 `GovernedToolSession.execute -> AgentToolInvoker -> AgentToolExecutionPipeline -> DefaultToolExecutor -> @Tool`，没有把原始 AgentTools 直接交给框架。

Session 是一次调用独有的状态。在完整模型响应交给 AiServices 前，先对整组 tool calls 做准入；任何一个需要审批，就保存加密 Checkpoint 并抛出类型化暂停信号，同组其他工具不执行，也不再请求模型。响应式模型包装器只转发 PartialResponse 和完成预检的 CompleteResponse；过滤 CompleteToolCall，防止框架提前执行尚未整批准入的工具。

框架响应式工具默认会调度到公共执行器。本项目通过 `executeToolsConcurrently(Runnable::run)` 显式传入直接执行器，配合立即返回已完成 Future 的受治理 ToolExecutor，使同批治理入口顺序执行；方法名带 Concurrently 不表示这里实际并行。真正的工具体仍在 Pipeline 的有界池中运行、执行超时与幂等策略。首个意外工具异常会阻止同批后续动作，不能任由框架收集异常时继续产生副作用。数据库及工具等待仍可能阻塞当前线程，不宣称整条链路非阻塞。

框架默认可能把 ToolExecutor 异常当成文本送回模型，本项目显式改为异常传播。可恢复的参数/工具错误已由 Pipeline 生成脱敏结果及恢复建议；建议放在工具观察内，不冒充用户指令。连续同类错误超限或策略拒绝后，下一轮关闭工具生成说明；若模型仍强行调用，则失败关闭。每个推理轮检查原 Run 的 iteration budget，模型和工具的实际尝试预算仍由各自网关计数。

AiServices 1.20.2 没有公开的“不新增用户输入，直接从工具结果继续”的入口。因此只有审批恢复使用 `DurableToolContinuation` 的最小原生消息循环：Worker 先重新鉴权并执行批准动作，续跑器从对应 ToolExecutionResultMessage 开始，复用同一 Session 治理，不重放动作、不伪造用户消息。现有审批现场只保存一个待审批动作，同批其他请求由恢复后的模型重新规划。

旧 ReActLoopRunner、同步/流式 StepProcessor、文本工具调用清洗器和固定反思评分已删除。框架窗口不按初始消息条数淘汰，实际送模仍按 Token 预算保留完整轮次，防止多轮工具把当前问题挤出上下文。

EnhancedRagPipeline 使用请求级 DefaultRetrievalAugmentor 串联查询转换、一次混合召回和聚合精排。身份通过服务端闭包绑定，Content 适配保留文档/分块/原始分数与父级元数据；不从模型文本取身份。框架执行器使用当前线程，避免默认无界扇出。此层返回检索证据，回答组装时才统一注入；预加载、searchKnowledge 和评测仍共用同一检索入口，不在 AiServices 上重复挂检索器。
