# 中文分块与检索改造规划

制定日期：2026-10-03。状态：中文句界、ICU 镜像与契约、一次分块双索引、维护重建入口及评测工具已实现并通过离线检查；真实基线、插件部署、历史批次与组合效果验收尚未执行。操作见 [中文检索与索引维护](./中文检索与索引维护.md)。

## 目标与当前证据

目标是优化中文知识检索，并让框架组件、业务适配与索引迁移的职责清晰。分块解决文档如何组成检索片段，分词解决 Elasticsearch 如何建立和查询倒排索引，两者分别验收。

规划起点为 LangChain4j 1.20.2、Elasticsearch 8.12.0：`TextChunker` 使用官方递归组件，ES 使用 standard，ensureIndex 仅检查存在性。本轮已切换显式 v3/rag_icu 配置并校验实际插件、Mapping 与 analyzer；黄金集固定路径已配置，真实标注文件仍需绑定本人来源后生成。

读取官方当前版本源码发现：`HierarchicalDocumentSplitter` 的重叠逻辑内部创建英文 `DocumentBySentenceSplitter`，没有公开的重叠断句注入接口。增加中文切分层不能等同于全面替换重叠算法。

## 推荐方案

| 部分 | 目标技术 | 原因与边界 |
| --- | --- | --- |
| 中文全文分词 | Elasticsearch 官方 analysis-icu 插件 | 支持 Unicode 和中英文混排；先以真实样本验证中文词界，不能承诺专业名词一定正确 |
| 文档中文断句 | LangChain4j 官方 DocumentByRegexSplitter 配置中文句末边界 | 使用框架组块与递归能力，规则清晰、无需调用模型；保留英文句子处理与长文本降级 |
| 分块组件装配 | 独立 Spring 配置提供 DocumentSplitter | 学习入口直接体现框架组件；TextChunker 专注章节与元数据适配 |
| 原文、引用与父上下文 | 原有项目适配 | 框架不提供完整业务合同，不能为了减少类而删除 |
| 索引治理 | 版本化 ES 索引与契约校验，复用持久索引任务 | 旧索引不会随配置变化自动更新；失败必须可识别、可重试 |
| 效果评测 | 原有 RAG 黄金集评测链路 | 对照 BM25、向量、RRF、精排各阶段，避免同时改变多项后无法解释收益 |

ICU 是推荐首选，实施前通过实际 Elasticsearch `_analyze` 与检索样本确认；如关键中文样本明显退化，再对照官方 Smart Chinese 插件后决定。不要同时维护多套可选分词引擎。IK 的自定义词典能力适合明确的领域词库需求，目前先使用官方插件减少额外维护。

## 第一批：建立真实基线

1. 使用隔离的验收用户和样本文档，准备至少 30 条人工标注问题：中文概念、中英混排、技术名/编号、跨句信息、代码/表格各 6 条。
2. 记录当前 standard 分词的 `_analyze` 输出，以及 VECTOR、BM25、RRF、RERANK 的 Recall@20、MRR@10、NDCG@10、Hit@5 和 P95。
3. 固定文档内容、Embedding 模型、精排模型、TopK 和查询输入；保存 RagQueryTransformer 的独立查询，扩展开关在对照期间保持相同。旧 RagQueryRewriter 已删除，若需要旧链路基线应明确使用旧版本。Agent 上游 Router 可能由模型补全检索问题，对照时也固定它的输出，避免把上游规划变化误当成分词收益。

主要文件：`config/rag-golden-dataset.json`（新增真实标注）、`src/main/java/com/ai/rag/eval/RagBenchmarkDatasetLoader.java` 与 `RagBenchmarkService.java`（复用现有行为）。黄金集标注属于评测数据，不新增仓库测试类。数据中的来源 ID 必须对应实际验收用户的文档，不能填伪造 ID 后宣称通过。

完成条件：有可复现基线报告，明确中文未命中的案例及其失败阶段，而不是只有最终回答截图。

## 第二批：优化 BM25 分词与索引契约

1. 在固定 ES 8.12.0 Docker 镜像中安装匹配版本的 analysis-icu 插件，通过 Docker 构建固定下来，避免每次手动进入容器安装。
2. 明确 ICU analyzer 的组成和 index/search 一致性，对正文、标题、章节采用统一规则；租户、用户与来源等过滤字段保持 keyword 精确匹配。
3. 对技术编号和模型名做检索检查，例如 `gpt-5.6-terra`、`/api/v1/rag/retrieve`。仅当样本显示退化时补充保留标识符的字段，不能把完整长正文当 keyword 来解决编号问题。
4. 将存在性检查升级为索引契约检查：检查目标版本、Mapping、analyzer 与必要插件。旧索引或缺少插件明确提示待迁移，不静默继续使用 standard。
5. 将 analyzer 与索引目标写在显式配置中，公共配置给出相同默认值，local/prod 只覆盖环境差异。

主要文件：`docker/elasticsearch/Dockerfile`（新增）、`docker-compose.yml`、`ElasticsearchFullTextClient.java`、`ElasticsearchProperties.java`、`application.yml`。实现时将部署和 Java 索引契约拆成独立任务。

先从旧 ES 文档建立新版本的索引，例如 `data-agent-rag-v3`；单纯更换 analyzer 可以使用 ES 重索引，不需要重新调用 Embedding。重索引前先冻结相关写入或安排补齐增量，核对成功/失败数量和身份字段后再切换配置，保留旧索引用于回退。不要向已存在字段原地修改 analyzer。

完成条件：实际 `_analyze` 和 BM25 对照通过，查询/入库分词一致，旧 Mapping 与插件缺失可识别，跨用户/租户结果为零。

## 第三批：优化中文分块与学习入口

1. 新增 `DocumentSplitterConfiguration`，统一提供官方 DocumentSplitter，删除 TextChunker 中原有的组件构建方法，避免重复装配。
2. 推荐递归链为：段落 → 行 → 中文句末边界 → 英文句子 → 空白词 → Unicode 字符。中文句末边界使用官方 DocumentByRegexSplitter，配置时保留句末标点，验证引号、连续标点和中英混排。
3. 保留 500/100 的当前字符单位用于第一轮公平对照；不要同时改 Token 计数、Embedding 模型和精排参数。
4. 继续使用 ChunkSourceLocator 校验来源位置，保留 emoji 代理对保护、结构标记、章节边界与父级范围。过长代码/表格可能跨块，不能承诺语法结构自动完整。
5. 明确中文重叠限制：沿用框架公开行为，用真实样本检查，不能依赖反射修改私有重叠组件，也不能复制框架整套切分算法。只有检索数据证明重叠不足造成明显漏召回，再单独设计下一轮方案。

主要文件：`src/main/java/com/ai/vector/DocumentSplitterConfiguration.java`（新增）、`TextChunker.java`；只在合同验证发现问题时调整 `ChunkSourceLocator.java`。中文句末规则是语言边界配置，不是模型语义切分。

完成条件：中文多句长段落优先在合适句界分块；无标点长文本能降级；正文非空白内容不丢失，来源位置正确、块大小受限、章节不混合，原有英文样本不退化。

## 第四批：处理分块变化后的双索引一致性

改变 analyzer 与改变 chunk 是两种迁移。ES 重索引只能重新分析现有块，不能重新生成中文分块。新分块必须由原文重新计算，并同时更新 Milvus 和 ES，不能只更新一边。

1. 先验收新上传文档，再核对文本知识、文件与长期记忆各自的重建入口；文件当前没有可直接调用的重新索引 API，不能把“重新上传文件”描述为已实现的历史文件迁移。
2. 复用 IndexTaskStore、IndexTaskWorker 和原有消费者，补足需要的重建入口与失败重试，避免再写一套并行调度器。
3. 使用一次分块结果驱动两边写入，核对 sourceId、chunkId、正文、原文范围与版本，避免两个消费者分别分块而生成不一致结果。
4. 当前 Milvus 未按分块版本完全隔离，因此采用受控维护窗口暂停受影响检索/写入，再分批重建。记录来源清单和状态，失败继续恢复。不能宣称 ES 单边切换就获得双存储原子更新或零停机回滚。
5. 长期记忆的向量重建只针对自身存储，不强行新增不需要的 ES 数据。历史主数据保留，不清空整个向量集合或业务库。

主要文件按实际任务拆分：`KnowledgeVectorIndexService.java`、`VectorMemoryService.java`、`FileProcessingWorker.java`、`IndexTaskStore.java`、`IndexTaskWorker.java` 以及对应受权限保护的重建入口。必要的新字段以设计确认后的具体合同为准，不为“版本化”引入完整平台。

完成条件：每个迁移来源两边 chunk 合同一致；失败可定位、可重试；删除与重建不会遗留旧块；用户/租户隔离保持。历史数据批量处理作为单独的执行步骤，开发时先使用隔离样本。

## 第五批：组合评测与交接

采用三组顺序对照：旧分块 + standard；旧分块 + ICU；中文分块 + ICU。先隔离分词收益，再看分块的额外影响。标注优先使用来源 ID，块 ID 或分级标注随分块变化重新核对。

建议发布条件：全组 Recall@20、MRR@10 不低于基线；中文组至少一项检索指标严格改善；技术编号和英文组无新增漏召回；同样预热条件下至少重复 3 轮，检索 P95 不超过基线 20%。这些是待测目标，不是当前成绩。现有评测质量门槛不改低以换取通过；不达标就保留原方案、分析失败样本。

复用 `POST /api/v1/rag/benchmark/run`，它要求 ADMIN 且按当前登录身份过滤，验收文档必须属于该身份。效果检查还需查看前端引用与原文位置，不能只看指标。实际运行可能调用查询向量化/精排服务，执行前明确使用的环境。

同步更新文档分块说明、RAG 链路和验收交接，标注真实通过与未验范围。保持中文有意义注释，不新增仓库测试类；关键失败用例放临时目录执行并保留验证报告。

## 实施原则与下一步

按第一批至第五批推进，每批留下可审查结果。首先建立基线，接着实施官方 ICU 分词与索引契约，确认收益后继续中文断句和双索引迁移。完整语义分块、领域词库、Token 分块与 ES 大版本升级留到有明确证据的后续需求，避免本次改动同时引入过多变量。
