# Supervisor 检查点与审批续跑

2026-10-10；LangChain4j 1.20.2 / agentic 1.20.2-beta30。当前完成源码改造与静态核对，尚未进行编译或真实运行验收。

## 实现范围

Supervisor 的 `local_assistant` 和直接绑定的专家可以暂停审批。检查点同时保存父协作事实与叶节点工具对话，批准后先执行获批工具、继续当前节点，再交回官方 Supervisor 选择后续节点，最后回答原问题。当前节点再次申请审批时，仍保存同一父协作现场。

更深层的“专家再委派专家”审批仍在暂停前明确拒绝：这一层还需要保存中间专家尚未结束的工具对话，不能只把最深层回答当成直接专家的最终结果。普通嵌套委派没有审批时继续沿用原路径。本批不是任意 DAG、并行节点或任意 Java 调用栈的恢复引擎。

## 框架与项目的职责

| 职责 | 实现 |
|---|---|
| 选择执行节点、参数绑定、节点串行调度 | 官方 `AgenticServices.supervisorBuilder` 和 `sequenceBuilder` |
| 共享完成事实和序列化 Scope | 官方 `AgenticScope.writeState`、`AgenticScopeSerializer` |
| 决策消息窗口 | 官方 `MessageWindowChatMemory`；保持用户/助手历史角色 |
| 工具对话与待审批原生消息 | 原 `GovernedToolSession`、`AgentCheckpointMessageMapper` |
| 授权、根预算、加密、审批事务、队列、恢复租约 | 原 Harness；框架状态不是执行授权凭据 |

没有注册新的全局 `AgenticScopeStore`，没有增加第二个任务调度器、数据表或模型客户端。Scope JSON 嵌入现有 AES-GCM 加密的 Run Checkpoint。框架默认序列化器的类型白名单保持原样，没有开放应用全包反序列化。

## 保存了什么

`SupervisorCheckpoint` 保存父 Agent/模型、首轮工具约束及工具数水位、稳定节点名与专家 ID 映射、父工具候选、父与当前叶节点的能力快照、待完成节点/任务、原始送模消息、Supervisor 决策历史，以及官方序列化的 Scope。

`SupervisorCheckpointState` 把完成账本写入 Scope 的 `harnessCompletedTasks`：每项只有节点名、真实 Agent ID、任务和实际结果。账本最多 256 项，Scope JSON 最多 1,048,576 个字符；整体 Checkpoint JSON 最多 2,097,152 个字符，超出即拒绝保存。这里限制的是字符量，不是精确 UTF-8 字节量。

待审批工具、参数、叶节点原生消息、叶模型、工具白名单和共享根预算仍由 `AgentRunCheckpoint` 保存。修复了此前用根请求的模型字段保存专家现场的问题，现在记录实际传入当前工具助手的模型配置 ID；空 ID 仍表示使用恢复时的默认模型，不代表固定了厂商模型版本。

## 恢复顺序

1. 原恢复 Worker 领取审批/根 Run 租约，解密 Checkpoint，重新校验申请人、审批人和获批工具。
2. `BackgroundUserScope` 加载启用用户及当前权限，为模型、Skill、检索和异步工具重建身份，不重放旧登录令牌。
3. 重新加载原叶 Agent 能力，与检查点取交集；核验主助手归属、启用状态和原专家目录。撤销原专家绑定、停用节点或撤销原父工具候选时失败关闭；新绑定不扩大旧现场。
4. 解码 Scope，验证完成账本与稳定节点目录匹配，恢复主助手到直接专家的防环路/深度路径，然后才执行已批准动作。获批动作仍走原 Pipeline、审批授权和沙箱幂等键；恢复不能凭空少算一层委派。
5. 将真实工具结果追加到原生对话，继续叶节点。再次审批时重新保存父现场，并维持 `WAITING_APPROVAL`。
6. 叶节点完成后把结果加入完成账本，创建新的官方 Supervisor 决策段。通过 `beforeCall` 导入应用完成事实，预填原决策消息，并在本次请求中提供审批续跑后的结果。
7. Supervisor 继续选择未完成任务，最终汇总原问题；写回同一个 Run 和原会话消息。

这是“节点边界续跑”：旧待审批节点直接由原生消息续跑完成，再进入新的 Supervisor 决策段。不会重新执行旧节点序列，也不导入框架私有的 `__planner_state_*` 游标。Scope 内原框架调用记录可以随 JSON 保存，但恢复依据只使用经过验证的应用完成账本。

同一节点收到完全相同任务文本时，复用已经完成的真实结果。模型把任务改写成不同文本仍可能产生新执行；这不是通用语义去重或跨系统 exactly-once。实际写操作仍必须依赖下游幂等和对账，不能只靠提示词“不要重复”。

## 暂停信号为何需要专门处理

直接专家先把根 Run 推进到等待审批，再返回自己的暂停结果。原委派管道可能把它包装成普通工具失败，或把“等待审批”当作成功文本交给管理者继续处理。

现在 Supervisor 作用域内的专家暂停统一转换成 `AgentToolSuspendedException`。Pipeline 只在受控委派且根 Run 已是 `WAITING_APPROVAL` 时透传这个信号；Supervisor 转成审批响应，不再执行下一次模型决策。本地节点同样先判断暂停，再检查运行是否活动，避免把正常等待误判为执行异常。

## 版本与部署

Checkpoint 合同从 v2 升到 v3；普通 v1/v2 工具现场仍可读取，其 `supervisor` 字段为空。v3 不可交给旧版本后端恢复，部署时不要混跑新旧审批 Worker。没有新增 Flyway 脚本；此前 V3～V8 的迁移是否已经执行，需要单独确认。

恢复段继续使用原审批状态订阅和最终会话写回，尚未接入后台 Run 的完整 token 事件日志，`eventHistoryComplete` 仍为 false。普通运行丢进程后的自动重放策略没有改变；只有已经成功保存的审批检查点可以恢复。Scope 不是长期记忆，完成事实随原 Run 检查点生命周期保存。

## 人工验收

以下为待执行步骤，并非本批已经通过的运行证据。先确认应用当前版本可启动、此前迁移已按部署顺序完成、RabbitMQ 可用，使用普通用户申请、另一个管理员审批。

1. 无审批协作：绑定两个只读专家，输入“先请需求分析专家拆分请假功能，再请风险评审专家检查遗漏，最后给出整合建议”。确认仍能正常协作与汇总，根预算累计正确。
2. 主助手节点审批：主助手绑定 `updateHotelPrice`，同时绑定一个只读专家。输入“先请专家说明调价前要确认什么，然后由主助手把演示酒店 HZ-001 在 2026-10-20 的豪华大床房价格改成699元，审批完成后总结实际结果”。确认计划确实为 Supervisor、本地节点发起审批；批准后原 Run 完成且写回原会话。
3. 直接专家审批：把调价工具绑定给“酒店调价专家”，主助手只绑定该专家。输入“交给酒店调价专家：把演示酒店 HZ-001 在 2026-10-21 的豪华大床房价格改成699元；审批完成后由你汇总结果”。确认批准后执行当前专家，然后管理者继续汇总，没有把专家的“等待审批”当成最终答案。实际工具参数以页面工具定义为准。
4. 重启恢复：使用第 3 条的新日期，等待审批时正常停止后端再启动，再由管理员批准。确认主助手、节点目录和已完成事实均恢复，根 Run ID 不变。
5. 同节点二次审批：明确请求两个不同日期调价，并要求等第一个动作返回后再做第二个。确认产生两张独立审批单；第一次批准不能授权第二次动作，第二次暂停仍携带同一父协作现场。
6. 权限撤销：暂停后撤销该专家绑定或停用专家，再批准。确认恢复失败关闭、待审批写操作没有执行，用户可见失败状态。
7. 取消与去重：暂停/恢复期间停止 Run，重复发送恢复提示，检查取消终态、租约和沙箱 `approvalId + toolCallId` 唯一键有效；原 Run 不重复写入。不要把这个沙箱结果推广成任意外部系统保证。
8. 嵌套边界：主助手只绑定专家 A，A 再委派 B 申请写动作。确认收到不支持该嵌套审批的明确拒绝，未创建不完整审批单、未执行写操作。

若第 2/3 条没有进入预期模式或节点，应先看请求计划、绑定和 Supervisor 决策，不能仅凭一句输入就宣称验证了对应路径。记录 Run ID、审批状态、工具流水、原会话最终回答和根预算，关闭 Debug 断点后再判断耗时。
