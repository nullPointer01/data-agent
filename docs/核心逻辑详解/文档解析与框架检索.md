# 文档解析与框架检索

2026-10-03：通用文档解析、中文句界、查询变换和向量 ContentRetriever 已迁移。框架为 LangChain4j Core 1.20.2，PDFBox/POI 解析模块为对应 1.20.2-beta30；PDFBox 3.0.7、POI 5.5.1。本轮验证使用真实框架和本地生成文件，未运行外部模型、Milvus/ES 或真实黄金集。

## 文档解析：框架提取正文，项目管理文件

从 [FrameworkDocumentFileContentParser](../../src/main/java/com/ai/service/file/FrameworkDocumentFileContentParser.java) 读起。FileParserService 根据文件类型路由：

| 输入 | 实际解析器 | 保留的职责 |
| --- | --- | --- |
| PDF | ApachePdfBoxDocumentParser | 文件存储、解析状态、归属和索引任务 |
| DOCX / PPTX | ApachePoiDocumentParser | 同上；不再手工遍历段落、表格和幻灯片 |
| TXT / Markdown / CSV 等受支持文本 | TextDocumentParser | 类型白名单和 UTF-8 文本输入 |
| XLS / XLSX | SpreadsheetFileContentParser | Sheet 名、制表符、日期、公式等原有表格输出合同 |

旧 PdfFileContentParser、DocxFileContentParser、PptxFileContentParser 已删除。官方 POI 解析器修正了旧 Word 实现把表格放在后续段落之后的问题。BlankDocumentException 映射为空正文：完成解析，不进入检索索引；损坏文件仍失败。不支持类型继续明确拒绝。

这里是文字提取，没有新增 OCR 或图片理解。FileMetadata 是业务实体，记录上传者、租户、存储位置、状态等；框架 Document 承载文本和文本元数据，不能替代业务数据库中的文件记录。

## 分块：中文句界进入官方递归链

[DocumentSplitterConfiguration](../../src/main/java/com/ai/vector/DocumentSplitterConfiguration.java) 装配：段落 → 行 → 中文句末 Regex → 英文 Sentence → Word → Unicode Character。Regex 保留中文标点和闭合引号，长句继续降级，装箱和重叠由框架执行。500/100 仍是字符参数。

TextChunker 组织章节、来源位置、结构标签和父上下文。框架可能重发只含重叠的短片段，来源定位采用覆盖终点对齐，再去掉没有新增原文覆盖的片段，防止重复索引；不会去掉原文中的重复段落。原文完整性不成立时拒绝生成引用。

框架内部重叠仍使用英文 OpenNLP，没有公开中文重叠注入接口。本轮增加中文切分句界，不宣称实现语义切分或完整中文重叠。详细限制见 [文档分块与框架适配](./文档分块与框架适配.md)。

## 查询变换：用官方组件理解追问

[RagQueryTransformer](../../src/main/java/com/ai/rag/RagQueryTransformer.java) 实现官方 QueryTransformer，删除原 RagQueryRewriter 的业务词表、类型猜测、关键词提取和 300 字截断。

| 条件 | 官方组件 | 行为 |
| --- | --- | --- |
| 明确问题，没有传历史 | DefaultQueryTransformer | 直通，无额外聊天模型调用 |
| 显式传入已鉴权历史，启用 compression | CompressingQueryTransformer | 将“它多久到账？”结合历史补成独立问题 |
| 显式启用 expansion | ExpandingQueryTransformer | 生成不同表述，主问题保留、去重并限制总数 |

公共配置 `app.rag.query`：compression-enabled=true、expansion-enabled=false、model-id=""、max-queries=3、max-query-chars=6000。model-id 留空使用当前租户默认聊天模型。模型通过 McpModelService 调用，预算、取消和模型异常保留，不新建旁路客户端。

现有 Agent Router 已经生成独立检索问题，因此默认检索入口不再次传历史。历史补全入口是 RagRetrievalService 的 history 重载，供取得合法历史的上游明确调用；前端没有新增历史参数，也不从检索模块反查任意会话。

RagQueryAnalysis 保留原 API 字段，keywords 返回空、queryType 返回 GENERAL，主查询与 variants 才是实际检索输入。不能继续声称有业务词表分类。查询扩展会增加模型和向量请求，默认关闭。

## ContentRetriever：现在调用在哪

此前 EnhancedRagPipeline 的 `contentRetriever(this::retrieve)` 已经符合 ContentRetriever 接口：Java 方法引用本身就是接口实现。但内部向量调用由业务服务手工串联，没有使用官方 EmbeddingStoreContentRetriever。

现在两层职责如下：

```text
EnhancedRagPipeline：DefaultRetrievalAugmentor
  → RagQueryTransformer：官方直通 / 历史补全 / 可选扩展
  → ContentRetriever 适配：DefaultHybridRetriever
      → VectorMemoryService：真实 EmbeddingStoreContentRetriever.retrieve(Query)
          → EmbeddingGateway：EmbeddingModel，字符串入口走 QUERY 用途与治理
          → MilvusVectorStoreGateway：EmbeddingStore，保留 collection 加载恢复
      → Elasticsearch BM25：相同问题变体和身份过滤
      → 一次框架 RRF 融合
  → 一次精排 → 父上下文 → 压缩 → 引用 / Trace
```

在 [VectorMemoryService.searchMatches](../../src/main/java/com/ai/service/VectorMemoryService.java) 看 `EmbeddingStoreContentRetriever.builder()` 和 `retrieve()`。两个 Gateway 是薄接口适配：复用原用途前缀、维度校验、熔断和 Milvus 恢复；不直接暴露原始客户端绕过治理。

框架返回 Content 的 SCORE、EMBEDDING_ID 和 TextSegment 元数据，适配回原响应。Content 不返回向量数组，下游也不读取数组；分数、主键、正文和引用位置仍保留。文档批量 embedAll 使用 DOCUMENT 用途，避免查询前缀污染入库。

变体实际参与向量召回，顺序执行、最多四条；同物理向量记录保留最佳命中，候选受 TopK 限制。ES 一次处理同一组变体，之后只融合一次。服务端绑定 tenantId/userId 和来源类型，模型不能决定权限。身份不完整时主 RAG 在进入模型和 Retriever 之前返回空结果。

不向 AiServices 无条件挂另一个自动 RAG：Agent 的知识预加载与 searchKnowledge 已共用受控入口，再挂一条会重复检索、消耗预算。框架组件已经在该入口内部使用。

## 本地验收入口

重启后先上传新的 DOCX（段落→表格→段落）、中文多句 Markdown 和 XLSX，检查正文、索引状态与引用位置。再问当前文档中的具体问题，断点依次放在 RagQueryTransformer.transform、DefaultHybridRetriever.retrieveWithTrace、VectorMemoryService.searchMatches、MilvusVectorStoreGateway.search。

开启 expansion 才应看到多次向量检索；普通明确问题默认只召回一次，且没有额外查询改写模型请求。追问通常由上游 Router 补全，不能仅凭未进入 CompressingQueryTransformer 就判定记忆没有使用。

历史索引没有自动重建。接续改造已配置 ES v3/rag_icu、严格索引契约、一次分块双索引及历史文件/记忆重建入口；部署与历史执行仍待验。见 [中文检索与索引维护](./中文检索与索引维护.md)。本文框架迁移的离线证据见 [验证记录](../../openspec/changes/framework-rag-components/verification.md)。
