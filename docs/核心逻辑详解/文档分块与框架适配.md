# 文档分块与框架适配

## 当前职责

文档分块已经迁移到 LangChain4j 1.20.2 的官方递归切分组件。`TextChunker` 作为知识、文件和长期记忆的统一入口，组织章节和业务元数据；分句、长度装箱、递归降级和重叠由框架执行。`EmbeddingGateway` 接收已经切好的 `TextSegment`，负责调用向量模型，既不切文档，也不决定每批写入多少条。

| 工作 | 当前实现 |
| --- | --- |
| 段落→行→中文句界→英文句子→词→字符的递归切分 | 官方 DocumentByParagraph/Line/Regex/Sentence/Word/CharacterSplitter |
| 分块大小和句级重叠 | 官方 HierarchicalDocumentSplitter |
| Markdown 章节、代码/列表/表格标签 | 项目 MarkdownStructureParser |
| 框架文本对应原文的字符范围 | 项目 ChunkSourceLocator |
| 子块的父级上下文范围 | 项目 HierarchicalChunker |
| 分批向量化、批量写入及治理 | VectorDocumentIndexer / EmbeddingGateway / MilvusVectorStoreGateway |

旧 `SmartTextChunker`、`SemanticChunker`、`SemanticChunk` 已删除，避免保留两个切分引擎。这里不引入模型语义切分，不调用聊天模型分析句意。

## 从哪里开始读

从 [TextChunker.split](../../src/main/java/com/ai/vector/TextChunker.java) 开始：

1. 结构解析器扫描原始正文，记录章节、结构类型和原文位置。
2. 按连续章节构建框架 `Document`，避免跨章节合并。标题相同但再次出现，也作为新的切分输入。
3. `splitter.split(document)` 返回框架 `List<TextSegment>`，这一步真正调用框架。
4. 来源定位器把每个结果对应回原始正文，补上字符范围和实际覆盖的结构标签。
5. 附加父级范围，生成稳定顺序的 `sourceId_chunk_n`，交给原有索引流程。

重点在 [DocumentSplitterConfiguration.documentSplitter](../../src/main/java/com/ai/vector/DocumentSplitterConfiguration.java)：Spring 集中装配公开的框架类，TextChunker 注入使用。中文句界由 DocumentByRegexSplitter 配置，保留句末标点、闭合引号和连续标点；没有使用框架 internal API。

为什么不直接只写 `DocumentSplitters.recursive(500, 100)`？临时验证复现了默认末级字符切分会切断 emoji 的 UTF-16 代理对，因此仅覆盖 `DocumentByCharacterSplitter.split(String)`，按 Unicode code point 提供字符单元。字符如何打包、递归调用和重叠仍由官方父类完成。这保护代理对，不等于按完整字形簇切分：组合音标、ZWJ 多码点 emoji 仍可能跨块。

## 大小与重叠

公共 `application.yml` 显式配置：

```yaml
app:
  vector:
    chunk-size: 500
    chunk-overlap: 100
```

local/prod 默认继承。单位是 Java 字符长度，不是 Token；emoji 等补充字符占两个 UTF-16 单元。参数必须满足 size > 0、0 ≤ overlap < size。若把 size 设为 1，又输入占两个 UTF-16 单元的字符，框架会拒绝无法容纳的文本，不会切坏字符。

500 是框架输出正文的长度上限。框架可能压缩/重组空白，所以包含大量空白的原文范围可能比输出正文更长。向量化时另外添加的用途前缀或文件名不计入此处限制。

100 是**完整句子重叠的上限**，不是固定窗口回退 100 字符。末尾句子太长就可能没有重叠；这与旧强切分回退固定字符的行为不同。中文切分层已优先按句末边界组织文本，但框架私有重叠组件仍使用随附的英文 OpenNLP 模型，不能宣称全面替换中文重叠或检索效果已提升。参数效果应重新用同一黄金集验证。

代码块、表格和列表会保留类型标记，但超长结构仍可能被切开，不承诺每个代码块/表格都完整，也不自动补表头、代码围栏或缩进。

## 为什么有来源定位器

框架返回块文本与序号，不返回原文字符偏移。你的引用、父级上下文和 ES 元数据需要原文范围，不能把输出块长度直接累加当作原文位置。

[ChunkSourceLocator](../../src/main/java/com/ai/vector/ChunkSourceLocator.java) 只适配位置：忽略框架调整的空白，按顺序对应所有非空白内容；允许框架产生的重叠，用全文覆盖约束处理重复文本的歧义。重复的相同内容可能存在多个等价匹配，返回一组满足顺序、覆盖和重叠上限的合法位置，不宣称知道框架内部选择了哪个重复位置。无法完整对应就明确失败，不能静默生成错误引用。

原 Markdown 解析器先把 CRLF 改成 LF 后再记录位置，会与 MySQL 中的原文错位。本次直接在原文上扫描 LF/CRLF/CR，并在后续定位时处理缩进和空白，因此下游仍可安全按原文 `substring(start, end)` 取得范围。位置按 UTF-16 计数，起始含、结束不含。

父级范围仍由原 `HierarchicalChunker` 按章节路径聚合同章节邻近块，默认字符跨度预算 1600。相同章节路径在文中重复时，父级规则仍按同路径处理；本次没有重做章节身份体系。它也不是另一套模型生成的摘要。

## 已有索引与验收

新上传或重新索引的内容会使用新切分器。历史 Milvus/ES 中的文本块不会因为替换 Java 类自动变化。本轮没有批量修改真实数据或启动自动重建。

对文本知识可在知识页面编辑并保存后等待索引就绪；检验新上传文档时使用新文件。历史文件及长期记忆需要通过各自已有的重建流程重新索引，不应只重建 ES 或只重建 Milvus。切分改变可能影响 `chunkId` 的含义，黄金集中的旧分块标注需要重新核对；不能把新旧切分的检索分数直接当作同条件效果对比。

建议在新文档中放入两个标题、中文长段落、重复句子、表格和代码块。在 `TextChunker.splitSection()` 的 `splitter.split(document)` 前后打断点，比较 Document、TextSegment 和最终 VectorChunk；再查看 `VectorDocumentIndexer.indexAll()`，确认这之后才开始调用 Embedding。

临时检查涵盖真实框架、原文完整覆盖、Unicode、CRLF/CR、重复内容、并发、知识/文件全文投影及向量元数据；未调用外部 Embedding、Milvus 或 Elasticsearch，真实质量评测仍待验。见 [验证记录](../../openspec/changes/framework-document-splitting/verification.md)。
