# 长任务上下文摘要

更新时间：2026-10-10。源码已实现，尚未编译、启动或进行真实模型/并发验收。

## 为什么改

原裁剪器把用户输入到下一条用户输入之前的所有消息连成一组。对普通多轮聊天，这能避免只留下回答；但 ReAct 长任务只有一次提问，后面可能有很多轮工具调用。保护当前提问就会连带保护全部工具历史，导致已经完成的旧步骤也无法压缩。

现在共用一套协议分组：历史用户对话保持整轮；当前提问单独保护；当前任务每批 assistant 工具请求及其全部结果组成原子组。旧的完整工具组可以摘要或裁剪，不能留下孤立工具结果。使用迭代并查集替代旧递归分组代码，不保留第二套分组实现。

保护内容包括系统指令、当前任务合同、当前问题、最近四条消息及其完整工具组、未完成工具调用/审批，以及官方 activate_skill、read_skill_resource 已加载的指令和步骤。新增摘要也受到保护；保护内容本身放不下时明确拒绝，不让模型靠猜补回约束。

## 运行链路

1. 同步/流式模型入口统一调用 `AgentContextGovernor`。先估算消息与工具定义；仍在输入上限内就直接放行，短问题不多调用摘要模型。
2. 超限且允许压缩时，`TaskContextCompactor` 先按当前模型、系统指令、当前问题和原消息位置/指纹复用根 Run 内已有摘要。源内容变化或变为保护内容后，旧摘要不能替换它。
3. 从最旧的可选完整协议组选择候选，最多 40 条消息。整个组超过摘要输入预算时跳过，不截断结果再冒充完整输入；至少两条源消息、有足够预估节省才考虑生成。
4. 通过官方 AiServices、原生 JSON Schema 和统一严格 OutputGuardrail，得到 `TaskSummary(excerpts)`。当前回答模型负责摘要，不新增模型记录、密钥或独立连接配置。
5. 每个摘录只有 sourceIndex 与 quote。Java 检查来源属于候选、quote 是对应消息的连续原文、数量/长度与去重条件；工具名称/调用 ID 从原消息补充，不能由摘要模型编造。
6. 将校验后的摘录作为带“不可信历史资料”说明的普通 AiMessage 放回原位置，替换被覆盖的完整组。原系统规则、当前问题和工具协议不变；不足以消除超限时继续裁剪其他可选完整组。
7. 摘要已经消耗模型预算，因此重新计算根 Run 剩余 Token 再准入回答，不能沿用摘要前的余额。

这是一版有原文依据的摘录式摘要，不让模型自由编写“已完成”“下一步”等未经证实的结论。摘要用于保留旧观察，任务目标仍来自原问题与任务合同，执行成功、权限和审批仍由服务端状态决定。

## 框架和项目分别负责什么

当前依赖的 LangChain4j 1.20.2 提供 MessageWindowChatMemory、TokenWindowChatMemory、AiServices、Schema 与 Guardrail；现有窗口类不能直接替代本项目的协议组、预算和审批保护策略。

框架负责模型协议、Schema、助手调用及结构化输出校验；项目只实现候选分组、原文证据校验、触发/复用策略和预算准入。`StructuredAssistantFactory.bind` 复用同一严格合同，不另建一套宽松 JSON 解析器。模型入口以回调传给治理器，避免 Spring 循环注入。

摘要助手不绑定 ChatMemory、ToolProvider，不能执行工具；其内部模型请求不给摘要回调，因此不能递归生成摘要。它继续经过同一模型入口、日配额预占/结算、根 Run 模型次数/Token、超时、取消和网络故障治理。结构化校验失败不自动修补重发；瞬时网络故障仍遵循现有重试策略，每次实际尝试单独计费记账。

## 次数与失败处理

| 情况 | 行为 |
| --- | --- |
| 上下文未超限 | 直接放行，不调用摘要模型 |
| 指纹完全匹配且复用后够用 | 复用摘要，不生成新摘要 |
| 摘要模型输出合法且原文匹配 | 接受并缓存，重新核算预算 |
| Schema 不支持、格式/原文不匹配、节省不足 | 丢弃本次生成结果，按协议组裁剪；已发生的模型用量照常记账 |
| 候选太大、预算/时间不足、次数耗尽或已有生成进行中 | 跳过生成，复用已有摘要并按需裁剪 |
| 取消、根 Run 终止、日配额不足、记账异常或身份拒绝 | 向上抛出，不降级成继续模型调用 |
| 所有保护内容仍然超限 | 返回明确的上下文拒绝原因 |

父子调用共享根控制器内的生成次数上限，同一候选批次不反复生成；网络等待不持有缓存状态锁，并发生成者不排队等待另一份摘要。默认最多两次逻辑生成，失败也占用次数；一次生成可能按现有策略发生多次网络尝试，不能把逻辑次数当成真实模型请求数。

## 配置与存储

公共 `app.agent.context.compaction`：

```yaml
enabled: true
model-summary-enabled: true
summary-input-tokens: 8192
summary-output-tokens: 768
minimum-savings-tokens: 1024
max-summaries-per-run: 2
```

local/prod 都显式启用模型摘要，其他数值继承公共配置。摘要输入估算包含 JSON、提示词及协议预留；输出设置进入官方 ChatRequest 上限。预估节省是嵌入的摘要相对源消息的输入差额，不保证单次调用总成本更低，因为生成摘要本身收费。

缓存只存在当前根 Run 的控制器中，保存短摘要与源指纹，最多跟随配置保留四份，不写 MySQL、Milvus、个人画像或长期记忆，不新增表或迁移。数据库聊天原文和框架窗口都不被覆盖，本批压缩的是实际送模副本。

审批仍保存原始消息现场；本批不更改 Checkpoint 协议。跨进程恢复后重新根据原文准入，必要时重新生成摘要，内存次数上限也重新建立；持久化根 Run 模型次数/Token 和日配额继续生效。不能宣称本批实现了跨进程摘要恢复、压缩框架内存或压缩审批载荷。

## 观察与验收

SSE `context_governed`、持久 Trace 与个人 Run 证据都只增加 `summary.outcome/summaryCount/coveredMessageCount/summaryTokens`，不写摘要原文。summaryTokens 是嵌入摘要的 Token 估算，不是生成费用。页面区分“送模消息数”与原始消息数，并显示摘要覆盖计数。旧 Trace 没有 summary 字段时仍可读取。

人工验收尚未执行。先完成前一批 Flyway V7 升级，避免日配额表缺失干扰模型调用。

1. 短请求：发送“用一句话解释 SSE”，应直接放行；不能只因摘要开关开启就增加一次调用。
2. 长任务：在专用本地验收配置中可暂将 default-model-window-tokens 调为 16384，保留输出预留 4096、安全边界 1024。绑定只读知识检索能力后输入：“围绕模型接入、工具审批、记忆和知识库检索，分别查相关资料，保留来源与关键原文，最后比较四条链路；找不到明确说找不到，不改动数据。”是否触发以真实消息 Token 超限为准，单个源组也必须能放入 8192 的摘要输入预算；过大组会跳过。验收后恢复原窗口值。
3. Debug：在 compact 的候选选择与 validateAndRender 处观察 sourceIndex/quote；在实际 ChatRequest 中确认旧组整体替换、任务问题原文保留、调用/结果成组、Skill 指令仍在。不要仅凭回答正确认定协议正确。
4. 复用与隔离：继续同一任务，源指纹匹配时应复用；切换用户、Run、系统指令或当前问题后不得复用。不同子调用共享次数限制，但只有同源内容才能共享摘录。
5. 不合格摘要：在受控调试中让响应包含不存在的 sourceIndex 或不在原文中的 quote，应丢弃并裁剪。框架格式校验不重发，真实调用仍计入用量。同一候选失败后不能每轮再试。
6. 预算与取消：剩余模型次数不足以容纳摘要和回答、时间不足 10 秒、预估 Token 不够时不生成。生成期间停止任务，取消不能被包装异常吞掉；根 Run 和每日账本均应计入已发生的实际尝试。
7. 审批恢复：触发审批后重启，仍从原始现场恢复并重授权，不重放已执行动作；不要求命中旧内存摘要。确认 Trace 与个人 Run 接口返回安全计数，消息中没有摘要原文泄漏。

## 限制

原文匹配只能防止凭空改写，不能证明摘录完整，也不能自动验证否定、时态和业务语义没有丢失；指令分隔与 JSON 转义也不是完全防注入。摘要仍是不可信资料，不能授权动作或当作执行凭证。

源组过大、事实不能压入输出上限、工具/Skill 保护内容过多时会跳过摘要或拒绝。当前覆盖活动 Run 的送模上下文，不是跨会话摘要系统、长期记忆，也不是持久后台任务。没有真实效果评测前，不宣称节省比例、召回质量或完成率提升。

后续批次继续审批事件，再推进持久 Run/重连订阅和 Supervisor 检查点。
