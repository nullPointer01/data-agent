# 常见陷阱

## 把 SQL LIKE 叫作全文检索

JPA LIKE 没有倒排索引和 BM25 分数，并且旧实现会在查询阶段扫描业务表、重新切 Chunk。它只能算低数据量兼容查询，不能作为 Elasticsearch 的等价降级。当前项目已经移除这条路径。

## 依赖 Elasticsearch 动态 Mapping

动态 Mapping 通常把字符串映射成 `text` 并附带 `.keyword` 子字段。如果代码对主字段执行 `term` 查询，可能出现索引有数据但租户过滤零命中的问题。RAG 索引必须显式声明精确过滤字段为 `keyword`。

## 原地修改已有字段类型

Elasticsearch 不允许直接把已有字段从 `text` 改成 `keyword`。应创建版本化新索引、全量重建并切换；旧索引清理由独立运维动作完成。当前版本为 `data-agent-rag-v2`。

## 吞掉索引异常

只记录 ES 写入异常会造成 MySQL、Milvus、ES 状态分裂，同时上层仍显示成功。索引服务必须暴露失败；跨存储补偿和重放需要单独设计。

## 把“接入模型”包装成“精排有效”

当前 `RagReranker` 已经接入真实 HTTP Cross-Encoder，并保留规则 Provider 作为 fallback，但代码可调用不等于效果更好。面试中可以说“实现了模型精排链路”，不能在同一黄金集的 MRR、NDCG、Hit@6 和 P95 对比完成前声称质量已经提升。评测时还必须检查 fallback 证据，否则一次实际使用规则降级的运行可能被误算成模型效果。

## 信任 Reranker 返回的候选索引

兼容 `/v1/rerank` 的服务可能返回乱序、重复、越界或缺失索引。直接按响应列表替换候选会错配引用，甚至把 A 文档的分数写给 B 文档。当前协调器使用原候选索引映射，要求候选完整且索引唯一，并拒绝非有限分数；契约错误按 fail-open 配置降级或直接失败。

## 只改 Embedding 模型名，不隔离向量索引

不同模型即使维度相同，向量空间也不兼容；维度不同则会直接触发 Milvus Schema 冲突。只修改模型名并复用原 Collection，会造成召回结果不可解释或写入失败。当前项目用 Embedding Profile 统一 provider、modelId、indexVersion、dimension、normalize 和 metric，并把模型身份编码进物理 Collection 名。

## 相信配置维度，不验证模型输出

OpenAI 兼容接口的模型名不能证明实际输出维度。配置 `384`、服务实际返回 `1024` 时，如果没有启动探测，问题通常要到首次写入才暴露。当前项目在启动期真实生成探测向量，并在每次 `embed` 后再次校验；不一致时错误会带出 modelId、期望维度和实际维度。

## 为已服务化的 Embedding 保留伪 Provider 开关

只有外部服务一条生产路径时，保留只接受 `api` 的 Provider 配置没有选择价值，还会让维护者误以为存在本地兜底。当前项目删除 `EMBEDDING_PROVIDER` 和 JVM 内嵌模型依赖，Profile 中的 provider 固定为 `api`，只用于 Collection 身份和诊断。Base URL、模型名和维度必须显式提供；服务失败会直接暴露，不静默切换模型。

## 原地复用旧 Milvus Collection

模型、维度、Metric 或向量处理策略变化后，应提升 `EMBEDDING_INDEX_VERSION` 并全量重建。版本化 Collection 会增加一段时间的存储占用，但比把新旧向量混在一起更可治理；旧 Collection 清理由独立运维动作完成，不在应用启动时自动删除。

## API Collection 未验证就删除 local Collection

Collection 创建成功不等于知识数据已经重建，更不等于召回可用。必须先完成 API Collection 全量写入，并用固定黄金集检查 Vector、BM25、RRF 和最终结果，再读取完整 Collection 清单、按精确 `__local__` 名称逐个删除。禁止通配符或前缀删除，禁止把旧向量复制到新 Collection，因为不同模型的向量空间不能转换复用。删除后的旧向量不可直接恢复，只能用旧模型重新生成。

## 把期望维度无条件作为 dimensions 请求参数

`EMBEDDING_DIMENSION` 是本地 Profile、返回校验和 Milvus Schema 契约，不代表所有 OpenAI-compatible 服务都接受 `dimensions` 字段。只有服务明确支持输出裁剪时才配置 `EMBEDDING_API_OUTPUT_DIMENSIONS`，否则留空；配置时必须等于期望维度，返回后仍要校验。修改任一维度配置都要提升 indexVersion 并重建。

## 在上游重复拼 query/document 前缀

E5 等非对称模型可能要求查询和文档使用不同前缀，但前缀必须只在 Embedding Gateway 边界添加一次。业务 Service 或 Chunker 再拼一次会改变输入契约并造成新旧向量不兼容。修改前缀必须提升 `EMBEDDING_INDEX_VERSION`，不能把新前缀生成的向量写入旧 Collection。

## 应用重试与 SDK 重试叠加

两层各重试三次可能把一次逻辑调用放大为九次网络请求，增加限流、延迟和费用。当前 LangChain4j 1.19.0 客户端显式配置 `maxRetries(0)`：该参数表示首次调用失败后的最大重试次数，因此 `0` 才是真正关闭 SDK 内置重试。Chat 与 Embedding 的业务级重试分别由项目执行器控制，不能再叠加模型客户端的重试。升级 SDK 时必须重新核对该参数的实际请求次数语义。

## 批量 Embedding 逐向量边校验边写入

如果第十个向量才发现维度错误，前九个已经写入会造成部分批次污染。正确顺序是先校验响应数量，再校验每个向量，全部通过后统一归一化并执行 Milvus `addAll`；主键数量通过后才能更新 Registry。批大小越大不一定越好，模板值只是未实测起点。

## 前后端各维护一份模型厂商模板

厂商 URL 和推荐模型变化较快，前端硬编码一份、后端再维护一份会产生漂移，切换厂商时还可能把旧 Base URL 留在表单里。当前 `ModelProviderCatalog` 是唯一来源，前端只消费安全元数据；运行时、发现和探测统一经过 Resolver，不能再复制端点规则。

## 把 OpenAI-compatible 当成全能力兼容

Chat Completions 请求可用，不代表 Tool Calling、JSON Schema、多模态、推理参数和错误格式完全一致。目录只承诺 Chat 基线，连接探测也只验证最小 Chat；专有协议必须增加明确 Adapter，不能通过改 URL 假装兼容。

## 把模型发现当成保存门禁

一些兼容厂商没有实现 `GET /models`，还有些账号只能调用已授权模型。发现失败只应提示手动填写模型 ID，真正的可用性由最小 Chat 探测判断；临时网络故障也不应阻止管理员先保存配置。

## 为连接测试绕过 SSRF 或复用正式缓存

Base URL 是用户输入，发现、探测和正式调用必须经过同一个 `OutboundUrlGuard`。企业私网模型或兼容网关需要通过部署配置显式放行，不能在探测接口留后门。探测客户端最多输出 32 token、不重试、不缓存，避免污染正式缓存或把一次点击放大成多次计费调用。

## 指定模型失败后静默切到默认厂商

显式选择的模型不存在、被停用或客户端构建失败时，如果自动回退默认模型，Prompt 可能被发送给用户未授权的另一家厂商。Registry 只能在调用方未指定模型且租户没有数据库默认配置时使用应用默认客户端；显式模型失败必须直接暴露。

## Base URL 改了仍复用掩码后的旧 Key

编辑页面显示的是掩码密钥，服务端只能在厂商和 Base URL 都未变化时从当前租户配置中取回真实值。只校验厂商会允许攻击者把 Base URL 改成自己的服务，再借发现或探测请求窃取真实 Key；端点变化且没有提交新 Key 时必须清空旧凭据并重新校验。

## 把 Agent 的停止按钮只做成前端 Abort

浏览器 `AbortController` 只能关闭客户端连接，不保证模型请求、工具调用或 Orchestrator 子任务停止。前端必须先从 `run_started` 取得 `runId`，调用节点内取消接口，再中止流；后端还要在迭代、模型和工具边界检查统一 Run 状态。取消是协作式的，不能承诺杀死已经发出的第三方阻塞请求。

## 让同步和流式入口各自决定 Agent 路线

如果同步默认走 Orchestrator、流式为了方便直接走 ReAct，同一个问题会因传输方式得到不同能力和 Trace。路线必须在 `AgentRunRouteResolver` 中独立于传输解析一次，SSE 只是 `AgentEventSink` 的一种实现。

## 为 Agent 配置维护一条旁路试运行协议

独立试运行需要额外定义记忆、工具副作用、审批和 Trace 语义，而且测试行为很容易偏离用户真正使用的正式链路。当前产品不提供旁路试运行；配置保存并设为默认 Agent 后，直接从正式对话验证并查看同一 Run 的证据和 Trace。

## 只限制 ReAct while 循环

只把硬编码轮数改成配置，仍挡不住 Fast Path、Orchestrator 并行专家、模型重试和工具调用消耗。预算必须下沉到共享 `AgentRunControl`，并在模型/工具真实边界原子准入；SDK 内部重试属于一次业务调用，不能重复扣业务调用次数。

## 在线程池里直接 set ThreadLocal

Orchestrator 线程池会复用工作线程，直接设置 Run Context 而不在 `finally` 恢复会让下一次无关任务读到旧 runId 和预算。异步任务必须经 `ContextPropagatingTaskDecorator` 捕获上下文，并用结构化 `AgentRunScope.run/call` 恢复父上下文。

## 只靠隐藏 ToolSpecification 做权限控制

工具列表是给模型的能力提示，不是服务端授权。兼容网关、模型幻觉或构造请求仍可能返回一个未展示的工具名。实际执行必须同时校验 Registry、Run RBAC 快照、当前 Agent 精确白名单和风险策略；拒绝必须发生在预算和反射调用之前。

## 用空 List 同时表示未配置、零能力和解析失败

能力配置里这三种状态的授权含义完全不同。如果 Entity 把非法 `tools` JSON 吞掉并返回空 List，而 Runtime 又把空 List 当作“全部工具”，一条脏数据就会变成 fail-open 扩权。当前项目只允许 legacy SQL `NULL` 保留默认 Tool 兼容语义，持久化 `[]` 表示零 Tool，解析失败抛出领域异常；JSON 编解码只能经过 `AgentCapabilityConfigurationCodec`，不能在 Entity 或新调用方里重新实现降级解析。

## 对所有工具统一自动重试

timeout 只说明调用方没有及时拿到结果，不代表下游没有产生副作用。只有只读、幂等、显式可重试并且属于明确瞬时故障的工具才允许内部重试。`toolCallId` 是关联编号，不是数据库唯一约束，也不能提供 exactly-once。

## 把原始工具结果分别写入日志、事件和 Trace

多处各做一次脱敏容易规则漂移，也可能在其中一个出口泄露 API Key、Bearer Token 或连接串密码。原始结果必须先经过统一 Sanitizer，模型、SSE、日志和 Trace 只消费同一个安全版本；参数只记录字段名、长度和摘要。

## 把审批当成权限提升

管理员点击批准只代表同意当前不可修改动作，不会替发起人补齐工具执行权限。人工等待期间用户可能被禁用、角色可能撤销、工具可能下线、Agent allowlist 或风险上限也可能收紧；恢复前必须重读全部当前状态并 fail closed，不能直接复用 Run 创建时的旧授权快照。

## 让并行工具调用在审批前执行一半

OpenAI-compatible 协议要求一条 assistant 消息中的每个 `tool_call` 都有对应结果。如果按顺序执行到审批工具才暂停，前面的动作可能已经产生副作用，后面的调用又没有结果，恢复后消息会非法。当前实现先预检整组请求，发现审批动作时只保存一个待审批调用，其他动作交给恢复后的模型重新规划。

## 把数据库租约说成 exactly-once

租约只能限制同一时刻哪个节点有资格恢复 Run，不能消除“下游已成功、本地成功状态未提交时进程崩溃”的窗口。沙箱依靠 `approvalId + toolCallId` 唯一键防重；真实外部写入必须让下游接受同一幂等键，或建立业务唯一约束、对账和补偿。

## 在调度线程里执行完整恢复链路

Spring 默认调度器可能只有一个线程。如果恢复扫描直接在该线程中调用模型和工具，同一个调度器上的续租任务就无法按时运行，长任务会在自己仍执行时丢失租约。扫描只能把候选 Run 提交给独立有界恢复线程池并立即返回；续租失败还要取消当前节点的 Run，确保后续模型和工具边界停止准入。已经发出的阻塞请求仍只能协作式停止，不能据此承诺强制中断。

## 直接轮换单一 Checkpoint 加密密钥

当前 Checkpoint 和原工具请求使用 `APP_ENCRYPTION_KEY` 整体加密，没有 key version。直接替换密钥会让等待审批的 Run 无法解密恢复。生产轮换前必须实现多版本解密、分批重加密和旧密钥退役流程。
