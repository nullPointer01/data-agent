## 项目 ① Data Agent · 拷打防御

### Q1: 为什么不用 LangChain4j 原生 ToolCall,自己设计文本协议是不是重复造轮子?

**业务背景**:公司内部和市面上的 OpenAI 兼容网关(同程内网网关 / Qwen / DeepSeek / 智谱)绝大多数是「透传 messages 字段」式代理,不支持 function calling 字段。原生 ToolCall 要么被网关吃掉,要么响应根本不带 tool_calls。

**技术决策**:用 `[CALL:tool("args")]` + 正则替代,LLM 输出 → 正则提取 → switch 分发 → 工具结果回填到 messages。

**为什么不选别的**:
- JSON 模式(force JSON output):强约束但兼容性更差,部分网关甚至不支持 response_format
- 自然语言解析:LLM 输出格式漂移概率太高,鲁棒性差

**代价**:解析鲁棒性弱于 schema 强约束(LLM 偶尔多输出引号或换行),靠 prompt 约束 + 正则容错处理。

### Q2: 多模型路由的缓存为什么是 ConcurrentHashMap 不是 Caffeine?

模型实例数量极少(单租户 5 个内),不需要 LRU 淘汰,ConcurrentHashMap 足够。失效走 Spring `ApplicationEvent`,因为模型配置变更是显式事件,不该等过期。引入 Caffeine 是过度设计。

### Q3: 向量库为什么是 Milvus 不是 Chroma / PgVector?降级方案怎么决定的?

- **Milvus**:Java 生态最成熟,LangChain4j 官方集成完善,384 维场景性能足够
- **Chroma**:Python SDK 主流,Java 集成不友好
- **PgVector**:得拉 Postgres,不愿为这个加一个数据库
- **降级方案**:开发机经常没启 Docker,启动时 socket 探测 19530 端口,不可达则用 InMemoryEmbeddingStore + 60s 定时落盘 + `@PreDestroy` 兜底。**生产必须 Milvus,InMemory 仅作开发兜底**

### Q4: 这个项目你说是 Claude Code 协作开发,具体哪些是你写的?哪些是 AI 写的?(这是必问)

诚实分层回答:
- **目标设定 / 架构选型由我主导**:「ReAct 用文本协议而非 ToolCall」「Milvus + InMemory 双模式」这些决策是我先有想法、再让 AI 帮我论证扩展
- **代码实现以 AI 协作产出**:类拆分、方法编写、配置代码 AI 完成更多,我读 + 跑测试 + 反馈迭代
- **Bug 排查、参数调优、性能验证由我亲自做**:落盘频率从 30s 调到 60s 是我跑出来的;ReAct 最大 8 轮迭代是我观察到死循环案例后定的
- **过程中我吸收了 LangChain4j 工程化实践**:对 RAG / Agent / Embedding 的理解是从这个项目学来的

**核心立场**:这个项目证明的是我「能把 AI 用起来落地工程」,不是「我从零写一个 Agent」。这恰好是 25 届 Java 工程师该有的能力。

### Q5: 项目跑得起来吗?有没有真实用户?

跑得起来,本地 + Docker Compose 都验证过。**没有真实用户,没经过千 QPS 压测**,所以技术选型偏保守(InMemory 兜底、8 轮迭代上限、token 计量预防失控)。**这个项目的价值不在产品成功,在学习路径与方法论沉淀**。

## 项目 ② 商品库数据拉取系统 · 拷打防御

### Q1: 红包匹配 15 亿 → 1400 万,具体算法是怎么改的?会不会漏匹配?(这是必问)

**原算法**:全量酒店 × 全量红包 × 多维度匹配规则,业务量增长后乘出 15 亿条结果集,DB 写入和下游消费都达极限。

**重构核心是业务建模,不是技术优化**:
- 原来:每家酒店都跟所有红包匹配,保留所有命中
- 现在:**「圈选某个星级的红包」识别为「该星级的默认红包」**,所有该星级酒店共用,不为每家酒店单独生成记录
- 配套:过期红包定时清理任务,避免存量红包堆积

**不漏匹配的保障**:
- 原算法所有 case 全覆盖(默认红包 + 个性化圈选都保留)
- 上线前用历史数据回归,确认 C 端展现红包跟之前一致
- 灰度先跑一周,数据量一致才全量

### Q2: 红包优化是你提出的还是上面要求的?(诚实拷打)

**诚实回答**:DBA 反馈红包表写入压力,leader 推动优化方向定下来,**业务建模重构是我和老员工一起讨论方案,定时清理 + 落地实现是我做的**。我不是发起者,但参与了业务建模决策,代码实现是我负责的。

### Q3: 冗余文件清理为什么不用 HDFS 这种自带清理机制的存储?

系统历史用 SCP 推 PB 文件到目标机,改存储动手术成本高,下游服务读取协议固定(扫描固定目录),改存储等于改协议。所以选了**在现有 SCP 链路上加一层后置清理**:
- 全量记录每个分片(维度 / 机器 IP / 时间 / 状态)
- 拉取后批量校验:有没有维度因机器宕机被重新分配
- 失败维度的残留文件主动清理(网盘 + 本地双路径)
- 清理失败邮件告警人工介入

**权衡**:这是「打补丁」式方案不是「换存储」式根治,但**短期收益高、风险低**。

### Q4: JVM 调优具体堆大小是多少?GC 收集器从什么换到什么?

(以下数字按实际口径,如有差异以你真实配置为准)
- 堆从 6G 调到 8G,新生代占比从默认 1/3 调到 1/2(因为拉取大量短生命周期对象)
- GC 从 ParallelGC 换到 G1,目标停顿 200ms
- Full GC 频次从「几秒一次」降到「数小时一次」

**调优思路顺序**(这个顺序很重要,体现你不是只会改参数):
1. 代码精简:发现内存暂存大量重复对象,List<Map> 重构成 List<DTO>,内存占用直接降一半
2. 内存结构:按维度全量加载改成分批 stream 处理
3. 参数调整:堆大小 + 新生代比例 + Survivor 区
4. GC 收集器:ParallelGC → G1

工具:jstat / jmap / GC log 分析(GCViewer / GCEasy)

### Q5: Redis 大 key 怎么拆?KVM 集群剩 < 1G 你怎么发现的?

**发现**:dbprometheus 监控大盘看到容量曲线接近上限,DBA 也告警。

**拆分策略**:
- 原 key:`hotel:relation:{hotelId}` 存酒店所有关系(产品/房型),最大单 key 几 MB
- 拆后:按业务维度拆,`hotel:relation:product:{hotelId}` / `hotel:relation:room:{hotelId}`
- 配套:写入侧改造保证多 key 一致性(transaction 或异步补偿)

**长期方案**:整体迁移凤凰集群(容量更大),KVM 退役。

### Q6: 千万级、300 维度、1 小时全量,数据是真的吗?

商品库团队对外公开的指标,goods-dashboard 监控大盘可见全量耗时和维度统计,我做拉取日常都看这些数据。**300+ 是核心维度数量**(库存、价格、房型、酒店关系、产品关系、政策、标签等),**千万级是几个核心维度的数据规模**,不是全部相加。

### Q7: SQLServer 错峰拉取是怎么做的?

hotel_product 是 SQLServer 一张大表,所有维度全量同时打它会把 DB 打挂。
- 把 300+ 维度按对 hotel_product 的依赖拆类
- 强依赖的串行队列,弱依赖的并行
- 配置化错峰间隔,避开高峰
- 配合 DB 监控数据实时调整

效果:DB CPU 峰值从近 100% 降到 60% 以下。

- 不是从 0 设计者,主链路框架是前辈搭的,我接手维护和迭代
- 大数据栈(Kafka + Flink + HDFS)实战不深,实际深度操盘的是上游团队
- 分库分表只是了解,商品库还没到必须分库的规模

## 项目 ③ 酒店收益策略预测系统 · 拷打防御

### Q1: 4 台机器抢任务,为什么不用 Redis 分布式锁?乐观锁冲突率多少?(必问)

**为什么选 DB 乐观锁 + IP 绑定**:
- 任务表本就在 DB,加 `update_locked_by_ip + version` 即可,不引入 Redis 依赖
- IP 绑定保证同一任务始终被同一台机器处理,避免任务跨机器迁移导致状态污染
- 乐观锁 `update where version=?` 一行 SQL 就是 CAS,代码极简

**冲突率**:30 秒一次轮询 + 任务量不大(每轮几十个) + 4 台机器,**实测冲突率几乎为 0**,因为状态机 + 时间窗口已把同时抢同一任务的窗口压得极短。

**不用 Redis 锁的原因**:任务长时间执行(分钟级),Redis 锁 TTL 难选——短了机器卡住任务被抢,长了机器宕机锁不释放,反而 DB 一致性更可靠。

### Q2: 32 线程线程池,为什么是 32?CPU 几核?

(实际口径)机器是 16 核,任务是 IO 密集型(大量 HTTP 调用),按经验值 IO 密集 ≈ 2N 取 32。

**为什么不动态扩容**:固定大小是为了不让大任务突发占满资源饿死小任务,突发流量靠**队列 + 拒绝策略**兜底,不靠扩线程。

**为什么不更大**:测试过 64 线程,反而因为线程切换开销和 GC 压力增大,QPS 没提升。

### Q3: 令牌桶 500 QPS 是怎么算出来的?突发流量怎么处理?

**500 是被调用方(在线/预览环境)的承受上限**,我和那边 owner 对齐过的。超了会被限流甚至拖累人家的真实业务。

**实现**:
- Guava RateLimiter,简单稳定
- 每个环境独立限流(在线 500 / 预览 500)
- 突发处理:RateLimiter 自带平滑限流,短时突发被拉成稳定流速
- 没用滑动窗口或漏桶,因为 Guava RateLimiter 性能成本最低,业务对限流精度不敏感

### Q4: 双环境对比预测在线/预览有什么区别?如何避免污染线上?

**在线** = 当前正式版策略(对照组),**预览** = 待上线新策略(实验组)。同一批样本同时打两个环境,对比指标差异。

**不污染线上的关键**:
- 调用「**预测专用**」接口,不是真正的下单/收益接口
- 接口走旁路:**只算分不写真实数据**
- 预览环境是独立服务实例,完全隔离
- 流量是模拟样本,不是真实用户请求

### Q5: 为什么用 DeepSeek 不用 GPT-4?27 个核心指标怎么定?

**DeepSeek 选型**:
- 内网网关已支持,不用额外申请 OpenAI 账号 / 处理跨境合规
- 推理成本是 GPT-4 的几十分之一,内部成本敏感
- 中文理解力够,业务报告用中文
- 实测对结构化数据生成 HTML 报告任务,DeepSeek 表现不输 GPT-3.5

**27 个指标**:从历史业务报表抽「运营最关心的差异点」——GMV / 订单数 / 转化率 / 房型分布 / 价格区间分布 / 客户分层等,**业务侧定义、技术侧落地**。

### Q6: 这个项目业务上效果如何?有量化数据吗?

**技术性能指标**:
- 单次预测 10 分钟内完成 14.5 万样本模拟、29 万次服务调用
- 上线前每个策略都跑预测,运营从「拍脑袋决定上下线」转向「看预测报告决定」

**诚实承认**:
- 我主要做技术实现,**业务效果数据(GMV 提升多少、风险拦截率)是产品/运营在跟踪**
- 这个系统是支撑系统不直接产生收入,价值在风险控制和决策提效

### 短板诚实承认
- AI 应用层主要是「调用 + 渲染」,**不是从零训模型**,是把 DeepSeek API 集成进业务流程
- **观察者模式实际是 Spring 事件机制**(`ApplicationEventPublisher`),不是手撸 Observer pattern
- 业务理解度有限,我懂这个系统怎么调度和呈现,**对策略本身的业务逻辑了解不深**
