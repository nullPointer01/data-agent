# 文档分块框架迁移

用户已明确要求继续迁移适合框架实现的部分；本轮接续文档分块讨论，直接实施，不再新增重复分块引擎。

## 设计

TextChunker 使用与官方 DocumentSplitters.recursive（当前 1.20.2）等价的公开 splitter 组合，以字符计数，500/100 默认值不变。按原始文本中连续章节范围分别调用框架；框架负责段落/行/句子/词/字符递归切分、大小限制和句级重叠。临时检查复现官方末级字符 splitter 会切断 emoji 的 UTF-16 代理对，因此仅覆盖该 splitter 的字符单元提取，使用 code point；组块和重叠不复制。保留 Markdown 章节/结构标签及父级上下文，这是项目业务合同。

框架文本可能调整空白且只有 index 元数据，增加专门的来源定位适配器：对原始文本与框架输出去除空白后顺序对齐，允许不超过 overlap 的前块重复，通过完整覆盖约束处理重复文本歧义，输出原文 UTF-16 起止位置。不重新实现切分算法；无法对应原文时拒绝生成伪引用。Markdown 解析保留 CRLF/CR 的原始位置，不再先规范化换行后当作原始偏移。

删除旧 SmartTextChunker、SemanticChunker、SemanticChunk 及仅由旧链使用的方法；统一文件/知识/记忆入口仍是 TextChunker。EmbeddingGateway/批量写入继续承担调用治理，不能为使用框架而绕过这些边界。

## 成功标准

执行者 Codex，环境 JDK17、当前真实 LangChain4j、本地 /tmp 验证，无模型/数据库调用：

- SC1 实际由框架递归切分，超长文本受大小约束、稳定 ID 和分块数量一致，无双引擎。
- SC2 中文/英文、Markdown、代码/表格/列表、CRLF/CR、重复文本、无标点长文本、Unicode 的非空白内容不丢失；返回片段与原文位置对齐；父范围包含子块。
- SC3 原有元数据、知识/文件入库消费合同保持，编译及针对性检查通过；不新增仓库测试类。
- SC4 文档说明框架重叠并非固定字符窗口、默认英文断句与中文局限、已有索引需重新索引后生效，无真实黄金集收益承诺。

不做：模型/库升级，数据库业务写入或自动重建历史向量，新的语义模型切分，整套文件解析/索引管道重构，前端修改。
