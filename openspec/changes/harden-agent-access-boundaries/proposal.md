# Proposal: Harden Agent Access Boundaries

## Objective

在不重写 Agent Runtime、RAG 和持久化审批状态机的前提下，加固个人 Agent 与管理控制台之间的访问边界。第一阶段解决已经确认的五类问题：管理能力仅由前端隐藏、普通用户无法安全读取可选模型、账号禁用和角色变更不能及时生效、自助注册可以指定任意租户、知识同步只校验租户而未校验创建人。

目标用户是使用个人 Agent 的普通用户和负责平台治理的管理员。完成后，普通用户继续保持简洁的个人工作区，管理员继续使用独立控制台，Harness 的业务执行语义不发生变化。

## Anti-Scope

- 不在本变更中新增 `PLATFORM_ADMIN`、`TENANT_ADMIN`、`BUILDER` 等角色，也不实现自定义角色编辑器。
- 不在本变更中拆分“用户确认”和“管理员审批”，不修改已有 Durable Run 状态机。
- 不开放用户自定义 Tool、Skill、MCP 或子 Agent。
- 不修改 RAG 排序、Embedding、Milvus、Elasticsearch 或模型调用协议。
- 不删除现有表，不迁移已有用户的租户数据。

## Quantified Success Criteria

- **SC-1 管理 API 后端保护**：100% 管理控制台使用的租户资源汇总、租户 Token 明细/重置、RAG 设置/健康/评估接口要求 `ADMIN`；个人 RAG 检索仍允许普通用户调用。
- **SC-2 用户模型目录**：新增 1 个普通用户可访问的只读模型目录接口，只返回当前租户或共享租户中已启用模型的非敏感字段；API Key、Base URL 和连接探测能力暴露数量为 0。
- **SC-3 实时账号状态**：每个受保护 HTTP 请求都以数据库中的当前启用状态和角色建立认证；被禁用用户的新请求授权成功数为 0；刷新令牌不能为已禁用用户签发新访问令牌。
- **SC-4 服务端租户分配**：普通注册请求不能决定 `tenantId`；服务端使用配置的注册租户，生产环境默认关闭自助注册。
- **SC-5 知识所有权**：知识同步配置的读取、保存、删除和手动同步均要求 `knowledgeId + tenantId + createdBy` 同时匹配当前用户。
- **SC-6 前端契约**：个人 Agent 模型选择改用用户模型目录；管理员现有模型管理页面和模型 CRUD 路径保持不变。
- **SC-7 兼容性**：分析、会话、个人 Agent、文件、知识、记忆、审批、Trace 和管理控制台现有 URL 不删除；本变更不修改数据库表结构。

## Assumptions

见 `sdd-assumptions.md`。核心假设是当前 `ADMIN` 继续表示平台治理角色；更细的组织角色模型在下一阶段单独设计。

## Boundaries

### Always

- 前端菜单隐藏只能改善交互，后端 Spring Security 和服务层所有权校验才是授权事实。
- 用户模型目录只提供选择 Agent 所需的最小字段。
- JWT 中的用户编号只作为查库索引，不能继续作为启用状态和当前角色的最终事实。
- 跨用户或跨租户资源统一返回“不存在或无权限”，不泄露资源存在性。

### Ask First

- 引入新系统角色、组织/工作区层级或邀请制租户成员模型。
- 修改管理员可管理的租户范围。
- 修改工具权限码、默认 USER 工具集合或审批角色模型。
- 修改数据库 Schema 或迁移已有用户 tenantId。

### Never

- 向普通用户响应返回模型 API Key、解密后的连接信息或管理员 DTO。
- 依赖 React 页面是否展示按钮来保护管理接口。
- 为解决鉴权问题绕过现有 Agent Tool Governance。
- 覆盖或回退工作区中已有的未提交变更。

## Verification Constraint

继续遵守用户已确认的项目约束：不新增或运行自动化测试，不执行 Maven 编译、打包、前端构建或 Docker 构建。实现阶段使用静态调用链检查、端点矩阵检查、敏感字段扫描和 `git diff --check`；真实 HTTP 鉴权行为保留为人工启动后的验证步骤。
